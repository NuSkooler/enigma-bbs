# Whats New
This document attempts to track **major** changes and additions in ENiGMA½. For details, see GitHub.

## 0.6.2-beta

* **New `%AV` animation view: frames played in a box over a menu's art.** Fire pillars beside a logo, an eye that glints every few seconds, a spinner next to the command prompt: the menu keeps taking input while they play, and only the cells that change are sent. Frames come from pipe-coded strings in the menu config, from one art file holding every frame (several animations can share one sheet), or from one art file per frame, found through the theme like any art, so themes and mods can supply their own. Place the box with an `%AV20` marker in the art, or with a `position` and no marker to animate existing art without editing it. Animations play on ANSI sessions only; PETSCII, ATASCII and RIP callers see the first frame. `menus.animations.enabled: false` in `config.hjson` turns them off everywhere, and `animations: false` in a menu's `config` turns off that menu. Stock menus do not use it yet; the templates show a commented-out example. See [Animation View](website/src/content/docs/art/views/animation_view.md).

  * **For mods:** a view may have a `prepare(cb)` method, which the form calls before it is first drawn (`AnimationView` loads its frames there). A form with no such view loads as before. See [Views that load before the first draw](website/src/content/docs/art/views/views.md#views-that-load-before-the-first-draw).

* **UTF-8 art with certain box-drawing or accented characters no longer breaks lines.** Characters such as `č`, `Ċ`, `┊` and `┍` in UTF-8 art were taken as a carriage return or line feed (their low byte is one), so the line was cut there and the rest drawn in the wrong place. They are now drawn as the characters they are. CP437 art is not affected.

* **Realtime interrupts are no longer drawn over, and the key that dismisses one stays with it** ([#1136](https://github.com/NuSkooler/enigma-bbs/issues/1136)). On a menu with `interrupt: realtime`, a node message, page or achievement is shown over the menu, whose forms stay underneath until it is reloaded. A `%TK` ticker or a `%SB` status bar with `refreshInterval` on that menu kept drawing its row over the interrupt, and the key pressed to dismiss it also reached the menu: it was typed into an `ET` command prompt, or ran the menu's action for that key, before the menu reloaded. While an interrupt is up the menu now draws nothing and gets no keys; a ticker in the interrupt's own pause prompt (the stock `pausePage` has one) still animates. The same goes for messages shown by a menu that could not go where it was asked to.

  * **The full screen editor's help no longer types into your message** ([#1137](https://github.com/NuSkooler/enigma-bbs/issues/1137)). The key pressed to close the Ctrl-O help screen was also inserted into the message body, and Escape moved the focus behind the help screen. The key now only closes help. The "added to your download queue" message after an export works the same way.
  * **The file list and WFC help pages** keep the key that closes them from the screen underneath too.
  * **A pause that clears the screen** is no longer drawn over by the tickers and status bars of the screen it replaced while it waits for its key. A clear-screen prompt without a pause behaves as before: the module that shows it owns the screen from then on.
  * **MRC and sysop chat** keep lines that arrive while something covers the screen, and draw them when it is gone.
  * After any of these, a ticker or status bar that missed a draw is drawn again in full.
  * **For mods:** new `client.captureInput(handler, { onMenuChange, onDrop })`, `client.releaseInput(token)` and `client.hasInputCapture()`; `MenuModule.coverScreen(options, fn, cb)` (and `coverScreen(client, options, fn, cb)` in `core/screen_cover.js`) for a screen shown over another; `View.suspendBackgroundDraw(client)` / `View.resumeBackgroundDraw(client, token)` and a `forceNextRedraw()` hook; `MultiLineEditTextView.addText(text, { redraw: false })` with `redrawChanged()`. `client.waitForKeyPress()` is unchanged: a plain wait, whose key also reaches the forms; wait inside `coverScreen()` (or take a `captureInput()`) to keep it from them. A cover cut short by a menu change (a sysop break-in, a time-up) no longer repaints over, or carries on in, the menu that replaced it. A `drawInBackground()` draw function should only draw: while the screen is covered it runs with its output discarded. See [When something covers the screen](website/src/content/docs/art/views/views.md#when-something-covers-the-screen) and [Covers and input capture](website/src/content/docs/modding/menu-modules.md#covers-and-input-capture).

* **A menu left while it is still loading stops there.** Leaving a menu while its art was still being drawn (at a baud rate, say) by a hotkey, a sysop break-in, a time-up or a disconnect let the menu carry on once the art finished: it built its forms, and started its `%TK` tickers and `%SB` status bars, behind the next menu, where their timers kept running. It now stops at the first step after it was left. A menu's `nextTimeout` (with `runtime.autoNext`) no longer moves on a caller who has already left that menu, and the message conference and area lists no longer send the caller back a second after a "Cannot change" message if they have gone elsewhere in the meantime.

  * **Art drawn at a baud rate is no longer broken up by a ticker.** While art was drawn with baud emulation (a menu's `baudRate`), a `%TK` ticker or `%SB` status bar already on screen drew between two pieces of the art, and the rest of the art was drawn from wherever that left the cursor. On PETSCII and ATASCII terminals the tick could also come out wrong. Background drawing is now paused while the art is drawn, and a ticker or status bar that missed a draw is drawn once when the art is done.
  * **The full screen editor's footer and quote window are no longer misplaced by a header ticker.** A `%TK` or `%SB` in the editor's header that ticked while the footer art (switching between edit and menu modes) or the quote window art was being read could make that art draw from the ticker's position. The header now waits until the art is drawn, then catches up. An error showing the footer art no longer leaves the screen's output held.
  * **An `mci` key that does not parse no longer hangs the menu.** A form key that is not two letters and a number (`tl1`, a typo) was warned about, and then the menu never finished loading. It is now skipped with the same warning, and the rest of the form loads. Keys such as `MET3` still configure view 3, as before.
  * **Posting with no current message area shows the no-access message** ([#1139](https://github.com/NuSkooler/enigma-bbs/issues/1139)) instead of throwing and leaving a broken screen. That happened for a user who had never been given a message area.
  * **For mods:** `MenuModule.hasLeftMenu()`, true once `leave()` has run, which the default `initSequence()` and the `prepViewController()`, `prepViewControllerWithArt()` and `displayArtAndPrepViewController()` helpers now check after their async steps (once the menu is left they still call back, with any form they built torn down); `MenuModule.setMenuTimeout(fn, ms)` / `clearMenuTimeout(handle)`, a timeout that `leave()` cancels; `View.setBackgroundInterval(fn, ms)` / `clearBackgroundInterval(handle)`, a timer whose drawing goes through `drawInBackground()` and that `destroy()` clears (`TickerView` and `StatusBarView` use it, unchanged otherwise); `View.isDestroyed(view)`; `MultiLineEditTextView.destroy()`. See [Leaving a menu](website/src/content/docs/modding/menu-modules.md#leaving-a-menu) and [Views that draw on a timer](website/src/content/docs/art/views/views.md#views-that-draw-on-a-timer).

* **Page sysop: the page form no longer takes keys under the "send as mail?" offer** ([#1138](https://github.com/NuSkooler/enigma-bbs/issues/1138)). If the sysop went away while a caller was typing a page, the offer to send it as mail was shown with the page's message field still taking keys underneath: what the caller typed went into the hidden field too, and one Enter answered the offer and sent the page again. At the "page sent" screen, the key pressed to continue was also typed over the art. Only the form on screen takes keys now.

  * **A menu that has been left can no longer take keys again.** A callback that finished after the caller had moved on (art that finished loading, a database read, a line from a chat server) could hand the keys back to a form of the menu that was gone, so keys typed on the next menu also reached it, action keys included. `leave()` now destroys the menu's forms for good.
  * **An interrupt pauses the forms its menu builds during it.** A form the interrupted menu builds while an interrupt is up (its art finished loading meanwhile) no longer draws its ticker over the interrupt. Tickers in the interrupt's own pause prompt still animate.
  * **New `pauseWhenInactive` view property:** a view that draws on a timer (a `%TK` ticker, a `%SB` status bar with `refreshInterval`) with `pauseWhenInactive: true` skips its ticks while its form is inactive or covered, and is drawn again when the form is active. It takes effect where a module deactivates or covers a form (`deactivate()` / `cover()`): the full screen editor and prompts, below. See [Form states](website/src/content/docs/art/views/views.md#form-states).
  * **For mods:** `ViewController.activate()`, `deactivate()`, `cover()`, `uncover({ redraw })` and `destroy()` (form states: [Form states](website/src/content/docs/art/views/views.md#form-states)); `View.suspendBackgroundDraw(client, scope)` and `coverScreen()` take an optional scope (`{ menu }` or `{ forms }`); by default a cover still pauses only the views that exist when it begins. `setFocus(true)` is `activate()`; `setFocus(false)`, `detachClientEvents()` and `removeViewController()` are unchanged (they detach and tear the form down; `detachClientEvents()` is deprecated in favour of `destroy()`). A form of a menu that has been left can no longer be attached again: see UPGRADE.md.

* **Tickers and status bars keep running in the full screen editor and under prompts.** A `%TK` ticker or a `%SB` status bar with `refreshInterval` in the editor's header, body or footer art stopped for good the first time the focus moved away from its form (from the header to the body, from the body to the Escape menu or find), and one in a form under a prompt (the message list's delete confirmation, the WFC kick confirmation and task prompt) stopped at the prompt. They now keep running while their form is on screen. A form that something is drawn over (a prompt, the quote builder, another footer in the editor's footer rows) pauses them, and draws them again when it is shown.

  * **The editor footer no longer stays attached under the Escape menu or find.** Keys bound on it in a theme (form 2) reached it while another footer was shown.
  * **A multi-line editor no longer moves the cursor back into itself after losing the keys.** A code just typed (`|12`) collapses 300 ms later; if Escape or another focus change came first, the line was redrawn and the cursor left in it while another field had the keys. It now collapses as the focus leaves.
  * **For mods:** `promptForInput({ prevFormName })` covers the previous form instead of tearing it down: its views and timers are kept, and its view listeners are removed, as before. Mods that extend the full screen editor: see UPGRADE.md.

* **Tickers and status bars keep running on screens that switch pages.** On onelinerz, rumorz and the BBS list (the list and the add page), the file list (browse and details) and the ActivityPub search, actor search and user configuration screens, a `%TK` ticker or a `%SB` status bar with `refreshInterval` stopped for good the first time the screen switched to its other page. The page not shown now only pauses them, and they pick up again when it is shown.

  * **Onelinerz and rumorz: the entry preview no longer draws over the list.** Typing a line and then pressing Escape within half a second drew the preview and the entry field over the list, and left the cursor in the hidden field. It also fired after leaving the menu. A pending preview is now dropped when the add page goes away.
  * **Leaving one of these screens while a page is still loading** (its art being drawn, a remote look-up) no longer draws the rest of a page shown before over the next menu, and the file list no longer jumps to its "no results" menu after the caller has gone elsewhere. A page shown for the first time can still draw its views once its art finishes, as before.
  * **The file list's "general" details section** no longer stays attached under the browse page after leaving details.
  * **For mods:** these modules cover the hidden page (`cover()`) instead of tearing it down with `setFocus(false)`. See UPGRADE.md if you extend one of them.

* **Views can be placed from menu or theme configuration, with no `%` code in the art.** An `mci` key with a `position` (`TK50: { position: { row: 23, col: 2 }, ... }`) creates its view there, as if the art held the code: useful where a code would draw over the art itself, such as a ticker over a logo. Any view can be placed, input views included. With a code in the art as well, the position wins, so a theme can move a stock view without editing the art. A theme alone can add or move views on a stock menu. Positions count from the art's top-left corner, so they follow art drawn lower down, such as a prompt. See [Placing Views from Configuration](website/src/content/docs/art/mci.md#placing-views-from-configuration).

  * **Placed views do not take Enter away from a form.** A form with no `submit: true` submits from the view with the highest configured ID, as before; placed views are left out of that choice.
  * **`mci` keys are checked against the art.** Views are matched by ID, so a key whose code is not the art's (`ET8` for a `%ME8`) still configures that view, as before, now with a warning in the log naming the menu, form and key. A key that is not exactly a code and an ID (`MET3`) still applies as read (`ET3`), with a warning. The stock menus and the luciano_blocktronics theme have been fixed to name the right codes.
  * **For mods:** an `mciMap` from `art.display()` remembers where its art was drawn (not one of its keys). `MCI_KEY_EXACT_REGEXP` is exported from `core/view_controller.js` beside `MCI_REGEXP`.

## 0.6.1-beta

* **Ticker text styles that change the text's length keep each character's colour** ([#1063](https://github.com/NuSkooler/enigma-bbs/issues/1063)). A `%TK` ticker with pipe colours in its `text` and a text-style `effect` coloured the wrong characters after any character the style turns into more than one: `upper` turns `ß` into `SS`, `lower` turns `İ` into two characters, and `mixed` does either at random. With `effect: upper`, `|14ßa|07b` drew `A` in the wrong colour and `B` in the view's colour instead of `|07`. Each character's colour now goes with everything it becomes. Setting `effect` on a ticker that already has text now restyles its text and colours together; before, the colours were left as they were, and switching from a text style to a dynamic effect such as `rainbow` left the text styled.

  * **The ticker's `firstLower`, `smallVowels`, `bigVowels` and `smallI` effects now style the text.** They had never done anything: the ticker passed those names straight to the text styler, which spells them `first lower`, `small vowels`, `big vowels` and `small i`, and the spaced spellings were not taken as text styles by the ticker at all. Both spellings now work.

* **A ticker no longer pulls the cursor out of the field you are typing in.** A `%TK` ticker redraws on a timer, and every tick left the terminal cursor at the end of the ticker, in the ticker's colour. On a screen with a text entry field, such as a main menu whose art has a `%TK` and whose command prompt is an `ET` view, the cursor blinked at the ticker, and a character typed after a tick was drawn at the end of the ticker, in its colour, instead of in the field. After each tick the cursor and colour now go back to the field that has focus, whether it is in the menu's art or in its prompt, and the cursor is hidden while the ticker draws. Screens with nothing to type into draw their tickers as before. That includes pause prompts, even one shown over a menu whose command field still has focus underneath (a realtime message, say): while the pause waits for its key, the field is set aside, so the pause's ticker does not pull the cursor back into it. For mods: a view that draws on its own timer can wrap the drawing in `drawInBackground(drawFn)` to get the same, and a focusable view says where its cursor goes by overriding `restoreFocusPosition()`. See [Views that draw on a timer](website/src/content/docs/art/views/views.md#views-that-draw-on-a-timer).

  * **Status bars with `refreshInterval` do the same.** A `%SB` view refreshing on a timer (a clock, say), in single or panel mode, moved the cursor out of the focused field in exactly the same way; it now puts it back after each refresh that draws.
  * **The full screen editor gets its cursor back too.** A multi-line edit view (`MT`) with focus, such as the message body in the full screen editor, now has its cursor returned to its edit row and column after a ticker tick or a status bar refresh.
  * **Custom info views put the cursor back in the field you are typing in, wherever it is.** After a module redraws its custom views (`%TL10` and up, through `updateCustomViewTextsWithFilter()`), the cursor went back only to a text field (`ET`) on the same form as those views. It now goes back to the field that has focus on any form, so a status line in a menu's art no longer leaves the cursor away from a command field in its prompt, and a multi-line (`MT`) or masked (`ME`) field gets its cursor back too. For mods: `repositionCursorToFocusedView(formName)` keeps its name, but no longer uses `formName` to find the view.
  * **MRC: a line arriving while you type no longer takes your next keys.** Adding a line to the MRC chat log left the cursor at the end of the log, so the next character typed into the input line was drawn there instead. The cursor and input colour now go back to the input line after every chat log line.

  * **The stock `pausePage` ticker now moves.** Its `bounce` text (48 columns) sat in a 60 column window, and `bounce` only moves text longer than its window, so it never moved. The template now uses `width: 34`, which fits between the `>>>` and `<<<` of the stock `pause_page` art. If your menu file came from the old template, set `width` under `prompts.pausePage.mci.TK1` the same way. The ticker and pause prompt docs had the same mistake in their `bounce` examples, and said the `scramble` and `glitch` effects override pipe colours; they keep them (only `rainbow` replaces them).

* **MRC: the multiplexer only listens on this machine, and the server's certificate is checked.** The MRC multiplexer, which the board's MRC chat sessions connect to, has no login, yet listened on every network interface and took each message's sender from the message itself. Anyone who could reach `chatServers.mrc.multiplexerPort` could post to MRC under the board's name as any user, read a user's private messages, or send MRC commands as them. It now listens on `127.0.0.1` only (so only programs on the board's own machine can reach it), and sends each message as the user its connection registered as, never as `SERVER`, `CLIENT` or `NOTME`. A user connected on two nodes, or back in MRC moments after leaving, is no longer logged off MRC when the other session closes, and a user leaving is logged off once rather than twice. A connection that gave no name could stop private messages reaching everyone else, a reset connection was never logged off or forgotten, a line split across reads was dropped, and a short line from the MRC server could throw; all fixed. With `useSsl` on, the connection to the MRC server was encrypted but accepted any certificate; it must now be valid for `serverHostname` (the default server's is), and the new `chatServers.mrc.verifyCertificate: false` turns this off for a private server. Thanks to zerosquaredio for the report.

* **`|TU`, `|NT`, `%TU` and `%NT` now draw their counts** ([#1105](https://github.com/NuSkooler/enigma-bbs/issues/1105)). The total users and new users today codes were the only predefined MCI codes giving a number instead of text, so a `|TU` pipe code was left on screen as typed, `|TU` in a message body or other body text changed the colour instead, and a `%TU` view in art stayed empty. They now give text like the other codes, and `{NT}` in a view's text is no longer left unfilled when there are no new users today. `{TU}` and `@sysStat:user_total_count` already worked and are unchanged.

* **Mods can ship default custom info formats** ([#447](https://github.com/NuSkooler/enigma-bbs/issues/447)). A module can override the new `getDefaultCustomInfoFormats(formName)` to return `{ 10: '{msgCount} new', ... }`, so its `%TL10`+ views are filled with no operator config. A `mainInfoFormat10`-style entry in the menu `config` or theme always wins, and an empty string hides a defaulted view. `getCustomInfoFormat(formName, id)` is the lookup, used by both `getCustomViewsWithFilter()` and `updateCustomViewTextsWithFilter()`; defaults are never written into the shared menu config. Existing modules have no defaults and behave as before. See [Default custom info formats](website/src/content/docs/modding/menu-modules.md#default-custom-info-formats).

* **Message lists can focus the last message when nothing is new** ([#447](https://github.com/NuSkooler/enigma-bbs/issues/447)). `msg_list` has a new `focusWhenNoneNew` option, `first` (default, as before) or `last`, set in the menu `config` or passed in `extraArgs` by a module that opens the list (`extraArgs` wins). With `last`, a list with no new message opens on its most recent message instead of the oldest. Returning from reading a message is unchanged. Nothing in the stock menus changes. See [Message List](website/src/content/docs/modules/message-lists.md#message-list).

* **New scan can skip the message base** ([#447](https://github.com/NuSkooler/enigma-bbs/issues/447)). `new_scan` has a new `skipMessageBase` config entry, the mirror of `skipFileBase`: with `true` the message base is not scanned and the module goes straight to the file base, so a board whose message reader is a mod can still run the file part of the login new scan (a `new_scan` entry with `skipMessageBase: true`, chained after the reader). With both set there is nothing to scan and the module finishes at once. Off by default; nothing in the stock menus changes. See [New Scan](website/src/content/docs/modules/new-scan.md).

* **Area hash tags given as a string are no longer stored one letter at a time.** An area's `hashTags` written as a string (`hashTags: uploads`) could reach a new upload as that string and be stored as one tag per character (`u,p,l,o,a,d,s`). File entries now take hash tags as a string, an array or a Set alike, trimmed and without empty tags. Entries already tagged that way keep those tags: look for single letter hash tags in the file base.

* **Uploads no longer end the caller's session on boards without a `fileBaseMainMenu`.** After every telnet/SSH upload, finished or failed, the upload module went to the menu `fileBaseMainMenu`, a name it had built in; on a board whose file base menu has another name, the caller saw "An unrecoverable error has been encountered!" and was disconnected. The upload menu now takes `uploadDoneMenu` in its `config` (default `fileBaseMainMenu`), and if that menu does not exist, or the caller may not enter it, the caller goes back to the menu they started the upload from, with a warning in the log naming the setting.

* **Release quarantined files, and an allowlist for false positives** ([#291](https://github.com/NuSkooler/enigma-bbs/issues/291)). `oputil fb quarantine list` shows what file scanning put in quarantine; `oputil fb quarantine release NAME [--area TAG] [--name NEWNAME] [--allow [--note TEXT]]` puts a file into the file base after checking that its SHA-256 is still the one recorded when it was quarantined, restoring its original name (refused unless it is a plain, safe file name) and importing it without a virus scan, with the uploader, description and TIC details its sidecar kept (sidecars now keep these); `oputil fb quarantine delete NAME` deletes one. The new **allowlist** is a global list of SHA-256 hashes you have declared safe: a listed file is clean, with `scanner: allowlist`, for every upload, REST upload, TIC import, `fb scan --virus-scan` and rescan, without any scanner running. It matches exact bytes only, lives in the file database, and only `oputil` can change it: `oputil fb mark-safe FILE_ID|SHA256 [--note TEXT]` (which also clears an `infected` result a rescan recorded on every entry with those bytes), `--list` and `--remove SHA256`. A release **scans the file first** (source `oputil`) and leaves it in quarantine if that scan rejects it or cannot run, so a held file is released once the scanner works again and a flagged one needs `--allow`; `--no-scan` releases unscanned on the operator's responsibility. `quarantine release ... --allow` adds a released file's hash (taken off again if the release fails). Every change, release and delete is logged with the operator's OS user. Rescan reports now list the `mark-safe` command beside the remove command. **Entries a rescan marked infected are now hidden from users** until you `mark-safe` or remove them: not listed, searched, picked up by a new scan, queued, sent, linked or served (web links made before the flag stop working, and a queued download is checked again right before it is sent); asked for by ID, link or REST they are simply not found, and a re-upload of the same bytes is still a dupe without the hidden entry being named. Also fixed: updating a file entry (`fb desc`, a TIC replace) deleted its user ratings along with the rows it then rewrote. Users passing the new `fileBase.scanning.infectedVisibleAcs` (default `GM[sysops]|ID1`) still see them, flagged by the file list's new `{infectedIndicator}` field; `fileBase.scanning.hideInfected: false` shows them to everyone as before. See [Releasing files and false positives](website/src/content/docs/filebase/file-scanning.md#releasing-files-and-false-positives) and [Hidden infected entries](website/src/content/docs/filebase/file-scanning.md#hidden-infected-entries).

* **Mods can ship their own art** ([#447](https://github.com/NuSkooler/enigma-bbs/issues/447)). A mod kept in its own folder (`mods/the_mod_name/the_mod_name.js`) can put its art in `mods/the_mod_name/art/`, and its menus name it by plain name (`art: MYMOD`). For menus whose `module` is that mod, art is now looked for in the user's theme, the default theme, then the mod's `art` folder, then `art/general`, so operators no longer copy a mod's art anywhere, and override it as before by dropping a file of the same name into their theme. Art names holding a path, single file mods (`mods/the_mod_name.js`), system modules and everything else are looked up exactly as before. See [Shipping art with a mod](website/src/content/docs/modding/menu-modules.md#shipping-art-with-a-mod).

* **Rescan the file base for viruses** ([#291](https://github.com/NuSkooler/enigma-bbs/issues/291)). Files already in the file base can now be run through the file scanners again, by hand with `oputil fb virus-scan CRITERIA [--older-than DAYS] [--max N] [--dry-run]`, or with the new built-in, manual-only `rescanFileBase` task from the WFC task list (give it a `schedule` and `args` in `config.hjson` to run it on its own). **A rescan only reports**: it never moves, quarantines or deletes a file or removes an entry. Each entry's result is recorded (`scan_result`, `scanned_at`, `scanner`, and the new `scan_signature` and `rescan_attempted_at`), and the operators get one private message per run, only when something needs them, listing each infected file with the command that removes it (`./oputil.js fb rm FILE_ID --phys-file`); an infected file is reported again on every run until it is removed. It uses the scanner entries whose `sources` include `rescan` (or list none), one file at a time so it never holds up uploads or TIC imports, reads only regular files inside their storage directory (never through a symbolic link), and stops when the scanner looks down. A scheduler `@method` can now call back with a short output text, kept as the run's `outputTail` and shown in the WFC task detail. `oputil fb rm --phys-file` now works before the file IDs as well as after. See [Rescanning the file base](website/src/content/docs/filebase/file-scanning.md#rescanning-the-file-base).

* **Users can choose between alternatives you offer** ([#447](https://github.com/NuSkooler/enigma-bbs/issues/447)). Where a board has more than one way to do something, such as the stock new scan and an index reader mod, each user can pick theirs. The choice is a user preference: a user property named `pref__<name>` (the `pref__` prefix is now reserved for this). The new `user_pref_select` module shows the choices you list in its menu `config` (each can carry an `acs`) plus "(board default)", marks the current one and saves on select; `@systemMethod:setUserPreference` does the same from a plain prompt with `extraArgs: { pref, value }`. Menus route on the choice with the existing `PV` ACS code, so the entry without `acs` stays the board default for everyone who has not chosen. Names and values are limited to what `PV` can test and are only ever taken from the menu configuration. Nothing in the stock menus changes; `main.in.hjson` and `login.in.hjson` carry a commented example. See [User Preference Select](website/src/content/docs/modules/user-pref-select.md).

  * **Enter now toggles an area on the configure newscan screen.** Its menu bound the key name `"enter"`, which ENiGMA½ never produces (Enter arrives as `"return"`), so Enter did nothing there. The stock template and the docs now use `"return"`. If your `message_base.hjson` was made from the old template, change `keys: [ "space", "enter" ]` in `messageBaseConfigureNewscan` to `keys: [ "space", "return" ]`.

* **New view: Table View (`%TV`)** ([#447](https://github.com/NuSkooler/enigma-bbs/issues/447)). A scrolling list laid out in columns, for screens such as message area lists. Rows can sit under group rows (`───── fsxNet ─────` dividers) and can be made unselectable; the cursor keys, Page Up/Down, Home and End skip them. Columns have widths (fixed, `fill` or a percentage), types (numbers right-aligned and sorted as numbers, dates formatted with `dateFormat`), formats, colours, and can hide themselves on narrow terminals (`minTermWidth`). A column can wrap long values onto several lines (`maxLines`), and `rules` change a cell's colour or text by its value (`when: "> 0"` lights a count, `when: "= 0"` shows `-`). An optional header labels the columns and marks the sorted one with ▲/▼, and the operator sets the sort (within groups; empty values last), which a module can let users change with a key. Pipe codes in fields a module marks as typed by users are shown as typed. In `theme.hjson`, a `TV` entry's `columns`, `stateSGR`, `sort`, `group` and `sortIndicator` merge with the menu's, so a theme can change one column alone; nested values on other views are still replaced. Without `columns`, `%TV` draws rows from `itemFormat` like `%VM`. Nothing in the stock theme changes. See [Table View](website/src/content/docs/art/views/table_view.md).

* **Uploads and TIC imports can be scanned for viruses** ([#291](https://github.com/NuSkooler/enigma-bbs/issues/291)). With `fileBase.scanning` enabled, every telnet/SSH upload, REST API upload and TIC payload (passthrough echoes included, so an infected file is never relayed to downlinks) goes through the configured scanners before ENiGMA½ opens it, before any archive extraction or `FILE_ID.DIZ` reading. The built-in `command` scanner runs a program such as `clamscan`, `clamdscan` or Windows Defender's `MpCmdRun` and reads its exit code, with `signatureRegex` and `infectedRegex` for its output; mods provide their own scanners through a `registerFileScanners` export, which both the BBS and oputil call. A rejected file is quarantined (renamed DOS style, `.exe` to `.ex_`, with a JSON sidecar) or deleted, per `failAction`, and the operators in `notifyUserIds` get one private message per upload session, TIC pass or oputil run. A scanner that fails or times out holds the file (quarantines it) unless its entry says `onError: accept`; a held TIC payload is instead kept in the inbound and retried, bounded by `tic.holdMaxAgeMs`, so a scanner outage loses nothing. Telnet/SSH callers see a rejected files page (new optional art `ULREJECT`) with a general reason, the rest of their batch going through as normal; REST clients get a `422`. `oputil fb scan` scans only with `--virus-scan`. Off by default. See [File Scanning](website/src/content/docs/filebase/file-scanning.md).

* **File scanning follow-ups** ([#291](https://github.com/NuSkooler/enigma-bbs/issues/291)). The docs now cover what ClamAV reports clean without looking: password-protected and encrypted archives (even with `AlertExceedsMax`; turn on `AlertEncryptedArchive` or `--alert-encrypted-archive=yes`, at the cost of rejecting every encrypted upload) and ARC and ZOO archives, which it cannot unpack. They also explain why a scanner that reads the file by path, the `command` scanner included, may not read the bytes ENiGMA½ hashed, and why that matters for TIC imports only. Each registered scanner is now logged, with the mod that registered it. For mod authors: a scanner's `init()` can call back `(null, { warnings: [...] })`, logged as warnings, while an error is logged as a failure to initialize; see [Writing a scanner](website/src/content/docs/filebase/file-scanning.md#writing-a-scanner). Also, for `main.js` and `oputil.js`: `--config` given a directory without a trailing slash (`--config /srv/bbs`) now finds `config.hjson` in it (it used to look for `/srv/bbsconfig.hjson`), `--config` may also name the config file itself (`--config /srv/bbs/config.hjson`), and a bare `--config` with no value warns and uses the default directory.

* **New MCI codes for message counts: `|NA`, `|NC`, `|NS` and `|AT`** ([#447](https://github.com/NuSkooler/enigma-bbs/issues/447)). Any art can now show the new messages in the caller's current area (`|NA`), in their current conference (`|NC`) and across their new scan areas (`|NS`, roughly what a new scan would find), and the total in the current area (`|AT`). "New" is what the new scan and the message list already count as new: after the caller's last read message, raised to their new scan date. They are cached for 10 seconds like `|NM` and `|NP`, but changing area or conference, changing the new scan selection or date, or reading messages counts again at once.

  * **`|NM` and `|NP` show the current count on first read.** They used to show the count from the previous read, so the first screen after logging in showed `0`, and a screen shown right after reading mail still showed the old count. They now count before they are shown, and reading mail counts again at once.
  * **For mods: `getMessageAreaStats()` and `markMessageAreaRead()`** in `core/message_area.js`. The first returns total, new, new-to-you and the last post for a list of areas in one database query, using the same "new" as above; the second marks an area read.

## 0.6.0-beta

* **v86 and Z-Machine doors handle time-up, hangups and a door that never starts** ([#1066](https://github.com/NuSkooler/enigma-bbs/issues/1066), [#1065](https://github.com/NuSkooler/enigma-bbs/issues/1065), [#1067](https://github.com/NuSkooler/enigma-bbs/issues/1067)). See [When the caller leaves mid-game](website/src/content/docs/doors/v86.md#when-the-caller-leaves-mid-game).

  * **Time-up.** When a caller's time for the day ran out inside one of these doors, they were sent to the time-up logoff, but the door kept running, and its output kept reaching their terminal over the logoff screen, until the connection closed. Both doors now detach the caller as soon as the time is up, or whenever the menu moves on while the door runs (an idle logoff, say), so the logoff screen draws with nothing from the door after it. A Z-Machine game is ended at once, as on a hangup.
  * **A v86 door is told the caller hung up, and gets time to save.** The emulator used to be stopped the moment the caller hung up, so a DOS door never saw carrier drop and lost whatever it had not yet written. ENiGMA½ now drops carrier (DCD) on COM1, as a modem would, and waits up to `disconnectGraceSeconds` (default `30`) for the door to save and exit before stopping the emulator; the same happens on time-up. The door's slot stays taken during that wait, so with `nodeMax: 1` a caller who redials at once may find the door busy until it has exited. A door still booting, and a server shutdown, get no wait. Set `disconnectGraceSeconds: 0` to stop at once, as before.
  * **A v86 door that never starts no longer leaves the caller at a spinner.** If the guest never wrote to COM1 (a bad image, a BIOS file that does not work, a `RUN.BAT` that hangs first), the `Loading...` spinner ran until the caller hung up. Now, if nothing arrives within `startTimeoutSeconds` (default `120`, `0` waits for ever), the emulator is stopped, a warning naming the image is logged, and the caller is told the door could not be started and goes back to the previous menu. The same message is shown for any other failure before the door's first output, such as a config problem, a missing BIOS or image file, or a guest that halts without writing anything; before, these went back to the menu without a word. See [When the door does not start](website/src/content/docs/doors/v86.md#when-the-door-does-not-start).
  * **Amiga doors accept `disconnectGraceSeconds: 0`**, which ends the session at once with no wait. Before, the lowest value was `1`. The default is unchanged.

* **A `FILE_ID.DIZ` or `README` in an archive's subdirectory, or as its only entry, becomes the upload's description** ([#901](https://github.com/NuSkooler/enigma-bbs/issues/901)). The upload scan found description files anywhere in an archive (`RELEASE/FILE_ID.DIZ`), but then read one from the wrong place when the archiver kept its path, as `unzip` and `tar` do; a lone entry in a subdirectory (`docs/manual.pdf`) was looked for in the wrong place when the archiver dropped the path, as `7za` and `unrar` do. Both are now looked for either way. An archive holding nothing but its `FILE_ID.DIZ` or `README` was handled as a single file and given a description made from its filename; a lone entry that matches `fileBase.fileNamePatterns` is now read as a description file. Names from the archive listing are untrusted: only a regular file that stays inside the extraction's temp directory is read, never one that a `..` or absolute name, or a symbolic link, points at elsewhere. A description file that cannot be found or read after extraction is now logged at debug level.

* **An empty flow file asks the BinkP mailer for a call, and is removed afterwards** ([#1047](https://github.com/NuSkooler/enigma-bbs/issues/1047)). [FTS-5005.003](http://ftsc.org/docs/fts-5005.003) uses a zero-length flow file (`touch 00010002.clo`, or one left by other software sharing the outbound) to mean "call this node even though nothing is queued", and §3.4 asks for it to be removed after a successful session. ENiGMA½'s BinkP mailer ignored these files: a node with only a poll file was never called, and the file was never removed. A zero-length `.ilo`, `.clo`, `.dlo`, `.flo`, `.iut`, `.cut`, `.dut` or `.out` now makes the node due a call on the next poll (the pull cycle, `binkpPullNow`, or crashmail), and is removed once a session with that node, outbound or inbound, ends successfully. It is removed under the node's `.bsy` lock, and only if it is still empty; a session that fails or is refused leaves it in place. Hold (`.hlo`, `.hut`) still means wait for the node to call us: an empty one is neither a reason to dial nor removed. `oputil bso status` and `bso list` show poll requests.

* **An SSH connection that stalls before login no longer keeps a node** ([#1080](https://github.com/NuSkooler/enigma-bbs/issues/1080)). An SSH connection counts against `general.maxConnections` from the moment it connects, but the idle timeout starts only at the shell, and SSH keepalives are off. A caller that stopped during key exchange or authentication kept its node until it closed the connection itself, so enough of them could fill every node. A connection that has not reached the shell within 120 seconds (the same as OpenSSH's `LoginGraceTime`) is now disconnected and its node freed. Set `loginServers.ssh.loginTimeoutSeconds` to change it, or to `0` to turn it off. Callers who log in normally see no change. See [Login Timeout](website/src/content/docs/servers/loginservers/ssh.md#login-timeout).

  * **A telnet connection ended by the board is closed even if the caller never closes its side.** After the board ended a session (logoff, idle timeout, a kick), the socket stayed open until the caller closed it. It is now closed 30 seconds after the last output has gone out, if the caller has not closed it by then.

* **A BinkP file we fail to store is left with the sender** ([#1090](https://github.com/NuSkooler/enigma-bbs/issues/1090)). When writing an inbound file failed (a full disk, say), an uncompressed file was still acknowledged with `M_GOT`, so the sender applied its disposition and could delete its only copy, and the file was handed on to the tosser. A compressed or zero-byte file was not answered at all, and the session waited out the five-minute timeout. Each is now postponed with `M_SKIP`, the partial temp file is removed, and the batch carries on; the sender offers the file again next session. A FREQ request (`.req`) that did not arrive whole (cut short, postponed, asked for again uncompressed, or the session dropped) kept the answering side from ever sending its `M_EOB`, and the session waited out the timeout too; it now finishes, and a `.req` sent again later in the session is still served. An empty temp file could also be left behind when a session ended while a zero-byte file was being written.

* **A long FTN export no longer has a second one run alongside it** ([#1079](https://github.com/NuSkooler/enigma-bbs/issues/1079)). The scheduled or requested EchoMail/NetMail export runs under a 10 minute watchdog. When an export ran longer than that, the watchdog gave up on it and released the export block and the outbound `enigma.bsy` flag, but the export itself kept running, so the next export started beside it. An export cannot be interrupted, so the watchdog now only logs, every 10 minutes, that the export is still running; no other export starts, and the flag stays up, until it really finishes. The `exportOutboundNow` task answers "An export is already running" for as long as that is true.

* **Terminal replies and arrow keys split across two network reads no longer turn into key presses** ([#942](https://github.com/NuSkooler/enigma-bbs/issues/942)). A terminal answers ENiGMA½'s connect-time queries (cursor position, device attributes, the CTerm capability queries) on the input stream. When the network delivered one of those answers in two pieces, say `ESC[<0;1;2` and then `;3;5c`, each piece was read on its own: the answer was lost and its digits, semicolons and final letter reached the menu as if the caller had typed them. An arrow or function key split the same way came out as letters too. The ANSI input decoder now holds the unfinished end of a chunk (`ESC [` and parameter bytes, nothing else) until the next chunk arrives, or for at most 100 ms, and decodes the two together. A lone `ESC` is still the Escape key at once, and no complete key is delayed. A split between the `ESC` and the `[` behaves as before.

* **The total user count stays current** ([#1049](https://github.com/NuSkooler/enigma-bbs/issues/1049)). `|TU`, the WFC's system stats, the REST `GET /_enig/api/v1/system/stats` route (`totalUsers`) and `@sysStat:user_total_count` in a theme showed the number of users from when ENiGMA½ started, so a new sign-up or a removed user was not reflected until the next restart. The count is now re-read from the user database when it is shown, at most once every 30 seconds; a new sign-up updates it at once, and a user removed with `oputil`, which runs as a separate process, is picked up within the 30 seconds. `|TU` still shows `1` when there are no users.

* **A local post in an area that is both ActivityPub and an FTN echo reaches the echo** ([#1032](https://github.com/NuSkooler/enigma-bbs/issues/1032)). When `activitypub_shared` is also mapped as an FTN echo area, a post ActivityPub delivered before the FTN export scan came round was marked exported, and the scan passed over it: with scheduled export it never reached the echo. ActivityPub now marks what it delivers with a state flag of its own (`ActivityPubExported`, `state_flags0` value 8; private mail also keeps `Exported`, value 2), which the FTN scan does not count. Posts marked before the upgrade are left as they were, so nothing already in the message base is exported. When FTN had already exported a post, ActivityPub's write also failed, and the post's ActivityPub Activity and Note IDs were not stored; they now always are.

* **EchoMail bundles hold bare packet names** ([#1078](https://github.com/NuSkooler/enigma-bbs/issues/1078)). FTN export gave the archiver each packet's full path in the export temp directory, so a bundle built with the default `InfoZip` archiver stored its packets as `tmp/enigftnexport-<session>/xxxxxxxx.pkt`. A tosser that extracts without stripping paths found the packets in subdirectories and might not toss them. The archiver now runs from the temp directory and is given bare packet names, as the Blue Wave and QWK packers already do, so bundles are flat whichever archiver a node uses (Info-ZIP, ARJ, RAR and LHA all store the paths they are given).

* **A BinkP session between two ENiGMA½ systems ends after a batch with a compressed file followed by an uncompressed one** ([#1043](https://github.com/NuSkooler/enigma-bbs/issues/1043)). When the receiving side got a GZ-compressed file (a packet, say) and then an uncompressed one (an archive) in the same batch, the second file could finish writing first. The receiver then closed the batch and opened the next one before it had acknowledged the first file, so the two sides counted that batch differently, and each waited for the other's `M_EOB` until the five-minute session timeout. No mail was lost, but the node's `.bsy` lock stayed held for those five minutes and the sending side logged a timeout. The receiver now closes a batch only once every file in it has been acknowledged or postponed. Sessions with binkd were not affected. A session torn down while a file is still being written no longer hands that file on afterwards. The change is on the receiving side, so an older ENiGMA½ receiving from an upgraded one can still stall the same way.

* **A file the remote already has is marked sent in its flow file** ([#1045](https://github.com/NuSkooler/enigma-bbs/issues/1045)). When a BinkP peer answered `M_GOT` for a file before we had finished sending it (it already held a copy), the file's directive was carried out but its flow file line was never marked `~`. A plain line was offered again every session and the node kept showing mail pending; a `^` line had its file deleted while the line stayed, so every later scan reported it missing until the flow file was edited by hand. The line is now marked exactly as after a full send.

* **ActivityPub inboxes accept RFC 9421 HTTP Message Signatures** ([#1025](https://github.com/NuSkooler/enigma-bbs/issues/1025)). Fedify-based servers (Ghost, Hollo) sign deliveries this way first, and Mastodon signs a delivery this way when it sends it again after a refusal. ENiGMA½ refused these with "Failed to parse HTTP signature", so a Fedify server had to send each first delivery twice. They are now verified, with the same minimum as the draft-cavage signatures every server still sends: method, target and host covered, the body bound by a covered `Content-Digest` (or `Digest`) that matches it, and a `created` time within 5 minutes. A request that carries both kinds is checked once, as RFC 9421. Behind a reverse proxy, the URL the signature covers is built from `overrideUrlPrefix`, not from forwarded headers. See [Signatures](website/src/content/docs/servers/contentservers/activitypub-handler.md#signatures).

* **Edit fields show the text they edit, from the first draw** ([#1034](https://github.com/NuSkooler/enigma-bbs/issues/1034)). A single-line edit field given a value with pipe codes in it (a location or affiliation saved with colours, say) drew the colours when the screen first appeared and the codes as typed once the field was redrawn, for example on moving to another field. MCI codes in the value (`|UN`, `{UN}`) were replaced on that first draw, though the code itself was what got saved. The field now shows the text as typed from the start, `|04` and `|UN` included, which is what it saves; sysop chat's input line still previews colour codes as colour. A focused field given text longer than itself now shows the end of the text, where the cursor is, rather than the start. A mask edit field (`%ME`) also draws what it stores on the first draw: a value given with its separators (`12/34/5678`) was drawn jumbled until the next redraw. A focused field given text also puts the cursor at the end of it, so the next key echoes there (it was left past the field). A theme or menu that set an edit field's `text` to pipe codes or MCI codes now shows those codes, and so does the upload screen's `blindFileNameText` (menu config), a label drawn into the filename field for blind uploads; see [Edit Text View](website/src/content/docs/art/views/edit_text_view.md#pipe-codes-and-mci-codes-in-the-text).

* **The full screen editor's `[ANSI] ` subject tag no longer cuts the subject** ([#1036](https://github.com/NuSkooler/enigma-bbs/issues/1036)). When the body is ANSI art (an uploaded ANSI file, or a reply to an ANSI message), the editor puts `[ANSI] ` in front of the subject. On a subject within 7 characters of the field's length (72 in the stock menus), that cut off its end, and taking the tag off again did not bring the end back. The tag is now added only when the whole subject still fits, and a subject that already carries it, also after `RE: `, is not tagged again (a reply to `[ANSI] My art` was `[ANSI] RE: [ANSI] My art`). The editor takes off only a tag it added itself, so a tag typed by hand stays.

* **SSH callers are turned away cleanly when every node is busy** ([#1017](https://github.com/NuSkooler/enigma-bbs/issues/1017)). With `general.maxConnections` reached, a new SSH connection used to hang during key exchange with no message, and its socket stayed open until the caller gave up. It is now shown *All nodes are busy. Try again later...* at the login stage (where the client shows it: OpenSSH does only when it has a terminal) and disconnected, and a refused connection is ended after 10 seconds whatever it is doing, its socket closed outright 2 seconds later if the caller has not closed it. Telnet callers get the message as before; WebSocket callers get it and then a close with code 1013 (*Try Again Later*). Each refusal is now logged. See [Limiting Connections](website/src/content/docs/servers/index.md#limiting-connections).

  * **A WebSocket session ended by the board closes the WebSocket.** Logging off, an idle timeout, running out of time or being kicked freed the node but left the caller's WebSocket open with nothing behind it, until the browser or web client closed it. The WebSocket is now closed once the last screen has been sent.

  * **The last output before a disconnect is no longer lost (telnet and WebSocket).** When the board wrote several things and then ended the session straight away (a goodbye message, the "module not found" notice), the last of them could be dropped, logged as "write after end". Everything written before the end now goes out first, and then the connection is closed.

  * **An SSH terminal size update sent before the shell no longer loses the terminal type.** A client that sent its terminal type, then a size change, then asked for the shell was treated as an unknown terminal type (the size was still applied). OpenSSH does not do this; the fix is for any client that does.

* **Art named by a relative path with an extension is found again.** A menu or theme naming art as a path relative to the ENiGMA½ directory, with an extension (`art: some/dir/FOO.ANS`), was looked for with the directory joined twice (`some/dir/some/dir/FOO.ANS`) and missed; ENiGMA½ then fell back to the theme and general art directories. It is now read from where it names. Names without an extension, absolute paths and bare names were not affected.

* **A hangup in a v86 or Z-Machine door frees its slot** ([#1021](https://github.com/NuSkooler/enigma-bbs/issues/1021)). A caller who hung up in either door kept one of its `nodeMax` slots until ENiGMA½ restarted, so after `nodeMax` hangups the door turned everyone away. Every way a session can end (a hangup, the emulator stopping or failing, a start-up step failing, such as an unsupported drop file type or an image that cannot be read) now frees the slot, ends the emulator thread and records the door run once. A caller who hangs up while a v86 door is still being set up is no longer left with an emulator running for nobody.

  * **v86 writes reach the image file when the session ends, hangup or not.** A v86 door's image was written back only when the door exited cleanly, so what a caller who hung up had written was kept only until the next restart, unless a later session exited cleanly first. It is now written back at the end of every session, and running sessions' images are written back when the server shuts down (up to 5 seconds; see [Stopping](website/src/content/docs/installation/production.md#stopping)). The image is written over the file in place and never truncated first, so a write cut short leaves a full-size image. A write that fails is logged and no longer stops later ones; writes no longer hold up other callers while they run.

  * **v86 images changed while the door is idle are picked up.** ENiGMA½ keeps one copy of an image in memory while sessions use it and for 10 minutes after the last one ends, and a session that starts on that copy first checks whether the file has changed on disk, reading it again if so. An image changed with `oputil v86` while nobody uses the door is no longer overwritten by the next session. A write that fails is logged and tried again at the next session end, and the copy is kept until it succeeds. See [When writes reach the image file](website/src/content/docs/doors/v86.md#when-writes-reach-the-image-file).

* **Sysop chat status fields now show the partner's name and elapsed time separately** in the `luciano_blocktronics` theme. The duration field had reused the partner field's ID, and the formats were attached to the views instead of the chat configuration ([#1058](https://github.com/NuSkooler/enigma-bbs/issues/1058)).

* **`binkp.pullSchedule: null` is no longer reported as a config error** ([#1041](https://github.com/NuSkooler/enigma-bbs/issues/1041)). The BinkP docs say `null` turns the pull cycle off, and it always did, but config validation (at startup and in `oputil config validate`) flagged it as a type mismatch. `null` and `""` both validate now. The docs also said leaving the key out turns the cycle off; it does not (the default, `"every 15 minutes"`, applies), and the docs now say so.

* **Pipe codes are measured the way they are drawn** ([#1022](https://github.com/NuSkooler/enigma-bbs/issues/1022)). One tokenizer now renders, measures, cuts and strips pipe codes, so text pads, centres and truncates to the columns it takes on screen. Before, `a || b` was padded as if it were six columns wide, `|CF05` as two and an unknown `|ZZ` (shown as typed) as none; the WFC task screen, which shows task output with its pipes escaped, padded short and wrapped early. Status bar panels set to `clip-left` and focused text fields that scroll now show the right part of a coloured value, cut by columns (wide characters included). Colours look exactly as before. See [Colour Codes](website/src/content/docs/art/colour-codes.md).

  * **Views measure what they draw.** Text views, menus and status bar panels pad and cut by the columns their text takes after rendering, so a pipe that is left over (`||07` shows `|07`, a code an edit field shows as typed) counts, and menu item positions and column widths no longer count colour escapes as characters.

  * **Message bodies:** `|1A`-style text shows as typed (it was colour 1, with the letter eaten), and `|CF05`, `|CB03`, `|CU01` and `|CD02` move the cursor by the full count in ANSI messages (they moved one column and printed the digits). `||05` is still a pipe and colour 05, as on Renegade, Synchronet and Mystic.

  * **Exports drop the codes a message draws, and only those.** E-mail, the full screen editor's export and the REST API now strip pipe codes the way NNTP, Gopher and ActivityPub do (the REST API used to strip only ANSI). A colour code or a known MCI code is removed; an unknown `|ZZ` is shown as typed, so it now stays; `|CF05` becomes five spaces, never more than the code is long, so an export is never longer than its input.

  * **Text styles change the text, not the codes in it.** `textStyle: upper` turned an ANSI colour into a "delete lines" sequence, and `lower` turned `|UN` into text; only the text is styled now.

  * A UI string that starts with an MCI code whose value is empty (`|LO` for a user with no location) shows nothing for it, instead of the raw code, and a cursor-forward with no count (`ESC[C`) measures one column.

  * **Typing colour codes in a single-line field stays inside the field.** While a code you just typed is shown as `|07`, it now takes its three columns: the field's fill no longer runs three cells past its right edge, the cursor sits after the code rather than on it, and a line near the field's width scrolls instead of spilling over. A scrolled field shows its full width of text; before, each colour code in view hid a character at the right edge. This is sysop chat's input line: it is the edit field that previews colour this way (a theme cannot give an edit field an `itemFormat`).

  * **Sysop chat input with wide characters.** The input line is measured in screen columns, so the cursor stays with the text when it holds CJK or other double-width characters, and a long line no longer pushes the prefix off its left end on a redraw. A `prefixFormat` that draws a literal pipe (`||`) is measured as drawn, so the cursor is no longer one column short, and with no `prefixFormat` at all a scrolled line holding colour codes shows the right part of the text.

  * **A button's `itemFormat` draws its text as it is.** A button (`%BT`) with an `itemFormat` or `focusItemFormat` rendered its (already rendered) text a second time, so a literal pipe in it could turn into a colour: a button labelled `a||07b` showed `a` and `b` in another colour instead of `a|07b`. The text now shows as it does without the format; the format's own codes still render. The same fix covers sysop chat's input line, whose redraw showed a typed `||`, or a `||` in its prefix, as one `|`. See [UPGRADE](UPGRADE.md).

  * **Ticker colours and cursor codes.** Ticker text whose only colour code comes first (`|04Hello`) now scrolls in that colour; before, it took the view's colour unless the colour changed again later in the text. A cursor-forward code (`|CF05`) now scrolls as that many spaces, and the other cursor codes (`|CB##`, `|CU##`, `|CD##`) are left out; before, they scrolled through the window in pieces, as a stray escape and visible `[5C`. A ticker scrolling left or right keeps its colours as the text wraps round; the copy coming in from the edge used to show in the view's colour, and the colours were off while the gap was in view. A text style effect (`lower`, `title`, ...) no longer treats a literal pipe (`||`) as the start of a code. This includes the WFC activity ticker.

  * **MRC `/rainbow` no longer cuts a colour code in half.** A long `/rainbow` line is still cut at 140 characters, but never inside a colour code, so the last word no longer ends in a stray `|0` on every other board. Room, user and site names sent through the MRC multiplexer have every code removed, including one that removing another code would form.

* **Stricter flow file path handling.** A flow file line's `^`, `-` or `#` (delete or truncate after sending) is now carried out only for a file inside the mail directories: the outbound directories, inbound, secure inbound, TIC transit, and any listed in the new `scannerTossers.ftn_bso.binkp.flowDispositionRoots`. A file elsewhere is sent and left in place, with a warning. A `#` line never truncates through a symlink. A flow file entry (or direct-attach netmail file) naming a file in ENiGMA½'s configuration, security, database or log directories is never sent. Finding a moved packet by name beside its flow file now applies only to packets, bundles and TICs queued for deletion from an outbound directory, never to a BSO control file; other entries in that situation are reported, not sent and not pruned. ENiGMA½ also refuses to write a flow file line that other mailers could read differently (a relative path, a control character, leading or trailing whitespace, a leading directive character, or more than 2047 bytes). `oputil bso list` marks entries `REFUSED`, `KEPT` or `MISFILED` accordingly. See [UPGRADE](UPGRADE.md) and [`flowDispositionRoots`](website/src/content/docs/messageareas/binkp.md#binkpflowdispositionroots).

* **Flow files are read the way other mailers read them, and rewritten atomically.** A line starting with `!` is now skipped like `~`, as already processed (it used to be taken as part of a path, and could be sent), `@` means send and keep, and a line starting with any other punctuation, or one with a control character, is left in place, never sent and never pruned; `oputil bso list` shows those as `UNKNOWN` or `INVALID`. A relative path is looked for beside its flow file rather than in ENiGMA½'s working directory. Marking a line sent, pruning, and dequeueing a superseded file echo file now write a new copy and rename it into place, so nothing reading the flow file meanwhile sees it empty, and every other line keeps its exact bytes, so paths written in CP437 or latin1 by other software are no longer garbled. A flow file owned by another user is changed in place instead. The same line queued twice is sent once and marked sent everywhere. Dequeueing a superseded file now removes a flow file left holding only `~` lines, as a session does, and says so in the log when the node was busy. A zero-length flow file (a poll request) is never removed. See [Flow file lines](website/src/content/docs/messageareas/binkp.md#flow-file-lines).

* **BinkP `.bsy` locks are no longer left behind by a shutdown or crash, and are no longer taken from a session still using them** ([#1052](https://github.com/NuSkooler/enigma-bbs/issues/1052), [#1053](https://github.com/NuSkooler/enigma-bbs/issues/1053)).
  * Shutting down during a BinkP session waited for the session to end, so the shutdown ran into its 15 second limit, exited with status 1 and left the session's locks behind; the node then stayed busy for up to 30 minutes after a restart. Live sessions are now sent `M_BSY` ("Shutting down") and closed, their locks released within 4 seconds, no new call is started (a call still connecting hangs up), and any lock still held is removed as the process exits.
  * A lock left by a crash or `SIGKILL` is removed at the next start, or at once by whatever next wants it, when it was written on the same machine by a process that is no longer running; otherwise after 5 minutes without being refreshed. Locks written by other software keep the `staleLockMaxAgeMs` rule. Machines sharing an outbound need their clocks within a few minutes of each other.
  * Held locks are refreshed once a minute, so a session longer than `staleLockMaxAgeMs` no longer has its lock reaped by the tosser, `oputil` or a second session. Releasing a lock removes it only if it is still the one that was taken, never another program's. If a session's lock is removed or replaced anyway, the session stops changing that node's flow files and stops deleting the files it sends from them; they stay queued and are sent again next time. ENiGMA½'s `.bsy` files now hold `<pid> ENiGMA <id> <token>` on one line. See [`staleLockMaxAgeMs`](website/src/content/docs/messageareas/binkp.md#binkpstalelockmaxagems).

* **A calling node's every address is locked, as binkd does.** When a node calls in presenting several addresses, ENiGMA½ now takes the `.bsy` lock of each one before reading any flow file, not just the first. A busy address with a session password makes the whole session busy (`M_BSY`, before the password is accepted, so nothing is sent or received), as binkd does; a busy address without one is left out of the session, and its mail waits for the next. Locks also cover flow files in a legacy or second outbound directory for the node, and are released only after the last flow file the session changed has been written. See [Busy nodes](website/src/content/docs/messageareas/binkp.md#busy-nodes).

* **NodeInfo active user counts are now users, not logins** ([#1023](https://github.com/NuSkooler/enigma-bbs/issues/1023)). `activeHalfyear`, `activeMonth` and (NodeInfo2 only) `activeWeek` counted login history entries, so a board of 5 users could report 140 active in six months. They now count distinct users whose last login is within 180, 30 and 7 days, capped at the total (counted live from the user database, not the startup value some other displays use), so they no longer depend on `statLog.systemEvents.loginHistoryMax`. The NodeInfo2 document (`/.well-known/x-nodeinfo2`) now has them under `usage.users` as its schema says, rather than under `usage`; NodeInfo 2.0 and 2.1 keep their shape. When the user count is not known `total` is left out instead of reported as 1. An index on last login timestamps is added to the user database at the next start (instant for any realistic board).

* **`oputil fb rm` and `oputil fb mv` no longer match files you did not name** ([#1020](https://github.com/NuSkooler/enigma-bbs/issues/1020)). A filename containing `_` or `%` was treated as a pattern, so `rm FILE_1.ZIP` also removed `FILEX1.ZIP` and `FILE-1.ZIP`. Those characters now mean themselves; `*` and `?` still work as wildcards.

* **RIPscrip support** ([#989](https://github.com/NuSkooler/enigma-bbs/issues/989)). A caller whose terminal draws RIPscrip graphics (SyncTERM with RIP enabled for the entry, IcyTerm in RIP mode) is now recognised at connect, by the RIPscrip version query or the terminal type `RIP`, and logged with the version it reported. Such a caller gets RIP on top of ANSI: `.rip` art where a theme has it, and a filter that keeps RIP commands out of everything else ENiGMA½ sends it. It matches `TE[rip]` in ACS, for menus of its own, and BBSDEV.DRP reports RIP as `Y`. There is nothing to configure. Other callers are sent the query and see nothing of it. See [RIP (RIPscrip) Callers](website/src/content/docs/servers/loginservers/rip.md) and [ACS](website/src/content/docs/configuration/acs.md).

  * **RIP art: `.rip` files.** A RIP caller asked for art `NAME` now gets `NAME.rip` when one sits beside the other art of that name, and otherwise what an ANSI caller would get. A `.rip` file is yours, so its RIP commands reach the terminal unfiltered; it may mix RIP command lines with ANSI text and MCI codes, which still place views where the terminal draws them. When the caller leaves a menu whose screen came from a `.rip`, its buttons and click regions are cleared, since clearing the screen leaves them clickable. Only art a theme or menu names is shown this way: a name holding a path, or one a caller could have supplied, is shown as text, filtered. No other caller is ever given a `.rip` file unless one is named outright, and then sees it as before. The [RIP callers page](website/src/content/docs/servers/loginservers/rip.md#drawing-for-rip-terminals) covers what to put in a `.rip` file for SyncTERM and IcyTerm, with a worked example.

  * **RIP callers are protected from RIP commands hidden in text.** A RIP terminal runs RIP commands wherever they appear in what it is sent, so text written by others (messages, user names, file descriptions, chat, oneliners) could draw over the screen, add invisible buttons or make the terminal type input as the caller. For a session with the RIP layer, everything ENiGMA sends is now made inert to RIP before it leaves: a NUL is put between `!` and `|`, bytes 0x01 and 0x02 (and so the CP437 smiley glyphs) are shown as `*`, and RIP's own `ESC[n!` sequences are dropped. This covers what ENiGMA itself sends: output of doors and of bridged systems (telnet bridge, BBSLink, DoorParty, Goldmine, ArchaicNet) is passed to the caller as the door or remote system sent it, unfiltered. (The Z-Machine door's games are run by ENiGMA itself, and their text is filtered.) Nothing changes for any other caller.

  * **MRC smilies stay as text for RIPscrip callers.** MRC chat can show `:)` and `:D` as the CP437 smiley glyphs, which are bytes a RIPscrip terminal reads as the start of a command. A caller whose terminal was detected as RIPscrip now sees them as typed, whatever `SHOWSMILIES` is set to. Other callers are unaffected.

  * **RIP starter menus.** Three RIP button screens for RIP callers (login matrix; a main menu with messages, who's online, last callers and goodbye; a message menu with list, post, change area and new scan), in front of the board's own ANSI menus, theme and art, which come back to them. Each button sends one letter, which typing does too. `oputil.js config new` offers them after the PETSCII and ATASCII questions, defaulting to no; on yes it adds the menu file, a `TE[rip]` branch on the connect menu and the art (generated `.rip` screens, each with an `.ans` of the same name) in the general art directory. No theme, no new setting; existing boards are not changed. See [Starter menus](website/src/content/docs/servers/loginservers/rip.md#starter-menus).

* **Early ATASCII support for Atari 8-bit style terminals.** SyncTERM and IcyTerm in their Atari modes (which announce the terminal type `ATASCII`), and anything connecting to a Telnet listener marked `emulation: atascii`, now get ATASCII: text, cursor movement and keys are translated on the way in and out, with no connect-time probing. An Atari screen has one colour, so colours are dropped and reverse video or a background colour is shown as inverse characters. The board stays ANSI inside, so existing menus and art are shown translated, in one colour and wrapped at 40 columns, until a theme is made for it. ANSI and PETSCII callers are unaffected.   * **CTRL W, CTRL Z and CTRL X are Page Up, Page Down and End for ATASCII callers.** An Atari keyboard has none of those keys, so every ATASCII session (in the starter menus or in menus of a board's own) reports CTRL W and CTRL Z as Page Up and Page Down (paging a message or a list) and CTRL X as End. ESC is the Atari's own Escape key, so the stock keys for the editor menu, finding (CTRL F, CTRL N, CTRL P) and quick save (CTRL S) work as they are. The board stays ANSI inside, so existing menus and art are shown translated and will look rough at 40 columns until a theme is made for it, with native PETSCII art (below). ANSI callers are unaffected. Along with it: additional named Telnet listeners (`loginServers.telnet.listeners`), each with its own port, `firstMenu` and `emulation`; the `TE[...]` ACS code for the session's emulation; and `info.emulation` in a theme. See [PETSCII (Commodore) Callers](website/src/content/docs/servers/loginservers/petscii.md).

  * **Native PETSCII art.** A theme for PETSCII callers can carry `.seq` files (raw PETSCII, as PETSCII editors export them) beside or in place of ANSI art; a PETSCII caller is shown `NAME.seq` as it is, in preference to other files of that name in the same directory, with views placed from MCI codes typed into the art. Boards that copied the theme earlier should copy the new `theme.hjson`; see [the note](website/src/content/docs/servers/loginservers/petscii.md#an-existing-board).

  * **F1 is Escape, F3 and F5 are Page Up and Page Down, for PETSCII callers.** A Commodore keyboard has none of those keys, so every PETSCII session (in the starter menus or in menus of a board's own) reports F1 as Escape (the full-screen editor's menu, backing out of a form) and F3 and F5 as Page Up and Page Down (paging a message or a list). * **enig-term, a browser terminal, is served at `/_enig/ws-term/`.** [enig-term](https://github.com/NuSkooler/enig-term) runs its emulation in WebAssembly and draws with WebGL, so callers get CP437 fonts, SyncTERM font switching, iCE colours and an optional CRT look with nothing to install, connecting to the WebSocket login server over `wss://`. ENiGMA½ generates the page's `config.json` from the board's configuration; the new `wsTerm` settings are `root`, `endpoint` (the public `wss://` URL, needed behind a TLS proxy) and `client` (options passed through to the page). See [enig-term Web Terminal](website/src/content/docs/servers/loginservers/enig-term.md).

  * **`install.sh` offers to install it**, defaulting to no: answer `y` (or set `ENIGMA_INSTALL_ENIG_TERM=yes`) and it downloads the latest release, checks it against the release's `SHA256SUMS`, and unpacks it into `ws-term`. See [Install Script](website/src/content/docs/installation/install-script.md#enig-term).
  * **The Docker image carries it**, pinned by `ENIG_TERM_VERSION` and a SHA-256 in `docker/Dockerfile`, at `/opt/enig-term`, and still off: set `wsTerm.root` to `/opt/enig-term` to turn it on. See [Docker](website/src/content/docs/installation/docker.md#enig-term-web-terminal).

* **SyncTERM-compatible terminals are asked what they can do, not judged by name.** When a terminal identifies itself as SyncTERM (or the new enig-term web terminal), ENiGMA½ now asks for its CTerm Device Attributes (`CSI < c`) and sets SyncTERM font switching from the answer, so SyncTERM in its curses mode, which cannot change fonts, is no longer sent font changes. The answer is kept per connection as `term.termCapabilities` (`fontSelect`, `brightBackground`, `mouse` and the rest) for code that wants it. Logins from SyncTERM 1.0 to 1.7 are also about 2 seconds faster: those versions never answer the OSC 8 query, and ENiGMA½ waited out a timeout for each of them. IcyTerm is asked for its CTerm Device Attributes as well (it answers from version 0.8.0; older versions do not answer, cost no timeout, and behave as before). Other terminals are not sent anything new. See [SyncTERM Style Fonts](website/src/content/docs/art/general.md#syncterm-style-fonts).

* **ACS `EC1` and `TM[...]` now work** ([#990](https://github.com/NuSkooler/enigma-bbs/issues/990)). `EC1` (UTF-8 terminal) never matched because the check looked for `utf-8` while ENiGMA½ stores `utf8`, and `TM[...]` never matched because it read a theme name that does not exist. The terminal now stores `utf8` whatever spelling of UTF-8 is assigned (`setClientEncoding` with `utf-8` included), and `TM[...]` matches the current theme's ID (a display name also matches if it has no spaces). Menu entries using either check will start taking effect. See [ACS](website/src/content/docs/configuration/acs.md).

* **Amiga doors run inside ENiGMA½.** The new `amiga_door` menu module runs AmiExpress (/X) XIM doors in an embedded vAmiga emulator (the `enigma-vamiga` package, with the AROS ROM bundled), so no external emulator, Kickstart or Workbench is needed. A small host shim on the door's disk image stands in for an /X node; the first session boots and snapshots the machine and later ones restore it in milliseconds, and the emulator's hard disk is the door's image file itself, so what a door writes goes into the image as it writes it, whether the caller quits or hangs up. Plain AmigaDOS programs that use standard input and output, as many Amiga BBS games do (Battle Grounds, Global War), run too with `doorType: cli`, the shim acting as their console. /X ARexx doors (`TYPE=AIM` scripts such as KickBoxing and Hacker) run with `doorType: aim` on an image that carries ARexx from your own Workbench 3.1 (`make_image.sh -w`), since AROS has no ARexx. Paragon doors, written for Paragon, StarNet and MAX's BBS and run by /X as `TYPE=TIM` (Master Space Empire, The Land of VEX, Sector Wars II), run with `doorType: tim`; `assigns` and `env` give a door the assigns and `ENV:` variables its install notes ask for. C-Net Amiga's ARexx pfiles (Bad Libs, Switchfont, Gold Mine) run with `doorType: cnetrexx`, also with your Workbench's ARexx: the shim is C-Net's `CNETREXX<port>` host, with its text codes and `###PANIC` on a hangup. See [Amiga Doors](website/src/content/docs/doors/amiga.md) and `misc/amiga_door/image/make_image.sh`.

  * **Door images are built with `oputil.js amiga-door`**, no Python or amitools needed: `create IMAGE DOORDIR...` writes the shim, its library, the startup sequence and your doors to a new FFS image (`--workbench` adds ARexx from your Workbench 3.1 disk), and `add`, `ls`, `extract` and `info` change and inspect an image, or any OFS/FFS `.adf`. `misc/amiga_door/image/make_image.sh` (xdftool) remains for machines without ENiGMA½.

  * **Upgrading:** run `npm install` to pick up the new `enigma-vamiga` dependency, 0.2.0 or later (the vAmiga 5 emulator core as WebAssembly, about 7 MB). No configuration changes are required; `doors.amiga.snapshotCacheEntries` (default 4) is the only new system setting.
  * **If you ran Amiga doors from a development build** (enigma-vamiga 0.1.x): door changes are now written as they happen, hangups included, instead of being copied back after the exits `persistOn` allowed. `persistOn` is ignored (the log says so once per door) and can be removed. The snapshot cache rebuilds itself. A session with a large image now needs far less memory (a 100 MB image: about 60 MB per session instead of about 340 MB), while an idle door costs about 40% more CPU (about 7% of a core instead of 5%) on the newer core.
  * **Shim 1.5:** the shim (axshim 1.5) now holds a caller's keys until the door reads them instead of dropping the end of a long paste, drives RTS, and takes the line rate from the door's `baud` setting. A door image keeps the shim it was built with: refresh an existing one by rebuilding it with `make_image.sh`, or replace just the shim with `./oputil.js amiga-door add IMAGE misc/amiga_door/bin/axshim C/axshim`.

* **ENiGMA½ now shuts down in order on `SIGTERM`, as it already did on `SIGINT`.** `SIGTERM` is what systemd, Docker and `kill` send, and it had no handler, so the process simply died: callers were dropped without a word and running Amiga doors never synced their images. Both signals now stop accepting new connections, disconnect callers with a notice, give Amiga doors up to about 3 seconds to sync, stop the scheduler and message networks, and exit 0. A second signal during the shutdown is ignored, and a step that hangs is given up on after 15 seconds, with the step named in the log and exit status 1. Also fixed: the shutdown started the file-area web service again instead of stopping it, and its last log lines were often lost. **PM2 users should raise `kill_timeout`**: see [UPGRADE](UPGRADE.md) and [Stopping](website/src/content/docs/installation/production.md#stopping).

* **`--config` keeps a board's files together** ([#927](https://github.com/NuSkooler/enigma-bbs/issues/927)). `paths.config` now defaults to the directory holding the loaded `config.hjson`, so on a board started with `--config` elsewhere a relative `menuFile`, achievements file or offline mail bulletin is found beside its `config.hjson`, as `includes` always were, instead of in the install's `config/` directory. The stock layout and a `paths.config` you set are unchanged. `oputil.js --config` follows the same rule, and `oputil.js config new` now writes an absolute `achievementFile` as it already did `menuFile`. See [UPGRADE](UPGRADE.md) and [Relative Paths](website/src/content/docs/configuration/config-hjson.md#relative-paths).

* **File Base handles bare `.gz` files as single compressed files.** It now lists and decompresses the inner file for description processing, while gzip-compressed tar archives keep using the tar handler.

* **Offline mail packets can carry bulletins** ([#893](https://github.com/NuSkooler/enigma-bbs/issues/893)). Callers who only read packets used to miss what online callers see at logon. Files named in the new `messageNetworks.offlineMail` block (`hello`, `news`, `goodbye` and a `bulletins` list) are now packed into every QWK and Blue Wave packet a caller downloads, converted to CP437; a relative path is taken from `paths.config`. * **QWK and Blue Wave packets share one area list and the online new scan pointers** ([#928](https://github.com/NuSkooler/enigma-bbs/issues/928)). Each format used to keep its own list of areas with a "newer than" date per area, so a caller who usually downloaded Blue Wave and then exported QWK once got everything again. Dates also missed echomail tossed in late with an older date, and a packet that was queued but never downloaded advanced them anyway, so its messages were never sent. Now one list serves both formats (a Blue Wave reader's offline configuration changes it for QWK too), and each area starts from the caller's ordinary new scan pointer, which moves only once the packet is actually downloaded. Existing callers' lists and dates are moved over once, the first time they export a packet, or upload a Blue Wave reply packet that changes their areas.

  **Callers who read both online and offline will notice:** a message read online is no longer packed, and a message downloaded in a packet is no longer new online. Setting a new scan date now also moves where the next packet starts. See [Areas and Scan Pointers](website/src/content/docs/messageareas/bluewave.md#areas-and-scan-pointers).

  Also fixed, in setting a new scan date and in the new-scan floor every new user starts with: a date now marks as new every message dated after it. Before, a message dated just after the chosen date that arrived after messages dated later, as echomail often does, made those later-dated messages count as read. The floor never applies to private mail: mail addressed to the caller is never treated as old. An area with nothing dated after the date counts as read; before, it kept its old pointer, so a new user saw an area's whole history until something new was posted.

* **`maxExternalSentAgeDays` on `private_mail` now takes effect.** Exported external private mail (FTN netmail, email) was always trimmed after 30 days whatever the setting said. It now honours the configured number of days, and `0` keeps sent mail. See [Sent Private Mail](website/src/content/docs/messageareas/configuring-a-message-area.md#sent-private-mail).

* **A blank date clears the newscan floor** ([#959](https://github.com/NuSkooler/enigma-bbs/issues/959)). Configure Newscan has always said the floor could be cleared, but `set_newscan_date` could only set a new date. With `target: floor`, submitting the date field empty now removes `newscan_min_timestamp`, and Configure Newscan shows `Floor: not set`. Set `allowClear: false` on the entry to keep a blank date an error. See [Set Newscan Date](website/src/content/docs/modules/set-newscan-date.md).

* **`new_scan` can scan the message base only.** With `skipFileBase: true` in its `config`, the new scan stops after the message base: the file base is not scanned and the caller's file base position is left alone, for menu trees with no file base menus or a "new messages" menu entry. Off by default; the stock menus are unchanged. See [New Scan](website/src/content/docs/modules/new-scan.md).

* **A deleted message's ID is never given to a new one** ([#958](https://github.com/NuSkooler/enigma-bbs/issues/958)). The message table handed a new post the ID of the newest message whenever that message had been deleted, by a sysop, an ActivityPub `Delete` or a caller deleting their own mail. Last read pointers, FTN export pointers and (since #928) QWK and Blue Wave packets all mean "everything up to this ID", so a post that got a reused ID could be skipped by new scan, by packets and by the FTN export. Message IDs now only go up. **Upgrading:** at the first start after the upgrade, ENiGMA½ rebuilds the `message` table once, keeping every message ID, all message meta and the full-text index, and logs when it starts and finishes. It may take a moment on a large board: a copy of a board with 36,000 messages (a 485 MB `message.sqlite3`) took about a third of a second. It needs free disk space for a second copy of the message table while it runs. See [UPGRADE](UPGRADE.md).

* **An edited ActivityPub post keeps its message ID** ([#964](https://github.com/NuSkooler/enigma-bbs/issues/964)). When a remote post was edited, the `Update` replaced the stored message with a new row under a new, higher ID: the post showed as new again in new scan and was packed again in QWK and Blue Wave packets, its view count went back to zero, any meta added after import was lost, and the old text stayed behind in the full-text index. An edit now rewrites the message in place, and replaces only the meta the edit carries. **Upgrading:** at the first start after the upgrade, ENiGMA½ rebuilds the full-text search index once, after the #958 message table rebuild, to drop the entries edits left behind; it logs when it starts and finishes. A copy of a board with 36,000 messages (a 485 MB `message.sqlite3`, with 336 such entries) took about one and a half seconds. See [UPGRADE](UPGRADE.md).

* **ActivityPub: an Update or Delete is accepted only from the object's author.** A validly signed `Update` or `Delete` from any remote actor could change or remove another actor's post, and its message, on the board. The actor whose key signed the request must now be the stored post's author (`attributedTo`) and the activity's `actor`, and an `Update` may not change the author. Only an actor itself may `Delete` its own actor. `Undo` of a `Follow` and `Reject` of a `Follow` are likewise refused unless the signer is the activity's `actor`, and an `Undo` of a `Like` removes only the signer's own like. A refusal is answered `401 Access denied`, like other refused inbox requests, and logged as a warning naming the object, its owner and the signer.

* **ActivityPub: remote actors are checked against the URL they came from.** A fetched actor was cached under whatever id its document claimed, so one server could plant an actor document, and key, for an actor on another server. A fetched actor's id must now be the URL that was fetched, on the host that answered (a key URL that answers with its actor only points at it: the actor is fetched from its own URL and must list that key). A WebFinger lookup by actor URL must point at the host that answered it; a handle's WebFinger may point at another host, as a split domain does. A remote actor's handle (`@user@host`) is used only when both the actor's own server and the handle's server confirm it, as Mastodon requires, and has control codes stripped; otherwise the actor is shown by its URL. Every inbound activity must be signed by its own `actor`. A `Create` is accepted as sent only from the Note's author, for a Note on the author's host; anything else, such as a reply forwarded by another server, is fetched again from the Note's own URL and stored as that server has it, in a `Create` built from that copy alone; a Note that arrives both forwarded and from its author is stored once. A forwarded `Delete` of such a reply is taken only when the Note's own server says it is gone: `410 Gone`, a `Tombstone`, or (as Mastodon answers for a deleted post) a `404`, which counts only for a public Note or when the board asked as a local user the Note was delivered to, since Mastodon also answers `404` for a post the asker may not see. It removes the Note only if it is stored as the `Delete`'s actor's. An `Announce` of a Note other than the announcer's own is likewise taken from the Note's origin, and an `Update` or `Delete` is checked against every stored copy of the Note, the same copies for both. A `Delete` of an actor that can no longer be fetched is accepted only when the actor's own server answers `410 Gone` for it, as Mastodon requires; a `404` may be transient and is not enough. The board's own fetches for these checks (a forwarded reply, a boosted Note, a gone actor) are signed, so servers that require signed fetches (Mastodon's secure mode, GoToSocial) answer them: as the user whose inbox received the activity, or, for the shared inbox, as a local user who follows the remote actor. With no such user they go unsigned, as before. The actor cache is emptied once at the first start after the upgrade, since a planted entry cannot be recognised; actors are fetched again as they are needed; a follower missing from the cache is fetched again in the background when a post, boost or like goes out, and gets it once found, while cached followers get it at once (one that cannot be fetched is not tried again for six hours), and a follower whose server has no shared inbox now gets them at its own inbox (it was skipped before). See [UPGRADE](UPGRADE.md).

* **The Docker image ships the archivers and description tools ENiGMA½'s defaults call** ([#905](https://github.com/NuSkooler/enigma-bbs/issues/905), [#906](https://github.com/NuSkooler/enigma-bbs/issues/906)). It lacked `unzip` and `zip`, so ZIP uploads -- the most common kind -- were filed with no listing and no `FILE_ID.DIZ` description, and its `unrar` was `unrar-free`, whose listing the `Rar` archiver cannot read, so every RAR looked empty. The image now has `zip`/`unzip`, RARLAB's `unrar`, `exiftool`, `pdftotext` and `xdms`, and [unarc](website/src/content/docs/configuration/archivers.md#unarc) 0.8.0, built for each platform, which reads ARC/PAK, ZOO, ACE, SQZ, UC2, `.Z`, xz, Zstandard, CAB, the C64 formats and Amiga DMS. Debian packages neither `unlzx` nor `atr`, so the image reads Amiga LZX and Atari ATR with unarc: the new `ENIGMA_UNARC_ARCHIVERS` environment variable, which the image sets to `Atr,Lzx`, points the named archivers at `Unarc` (a complete entry for the same archiver in `config.hjson` replaces it; outside Docker, nothing changes unless you set it). The image build now fails if any program a default archiver or description tool calls is missing. Files stored while a tool was missing can be re-described with `./oputil.js fb scan --full --update AREA_TAG`. See [Docker](website/src/content/docs/installation/docker.md#archivers-and-file-descriptions).

* **`install.sh` recommends unarc** ([#907](https://github.com/NuSkooler/enigma-bbs/issues/907)), now that 0.8.0 is on crates.io (`cargo install --locked unarc-cli`), along with `zip`/`unzip` and RARLAB's `unrar` in place of `unrar-free`.

* **Uploads that a sender ends badly are no longer thrown away** ([#914](https://github.com/NuSkooler/enigma-bbs/issues/914)). A YModem upload from the VTX web terminal always failed, though the file had arrived intact: after its last block VTX sends cancel bytes where the end-of-batch block belongs, `sexyz` exits with an error, and ENiGMA½ discarded the whole upload on that exit code. Protocols can now say they write a `DSZLOG` (`dszLog: true`, set on the predefined SEXYZ protocols); when one exits with an error, the files its log records as received in full, and only those, are kept, and the log says so. An upload the log does not confirm fails as before. See [File Transfer Protocols](website/src/content/docs/configuration/file-transfer-protocols.md).

* **`loginServers.telnet.enabled: false` now turns Telnet off.** Since 2018 a server's own `enabled: false` was read from the wrong place and ignored, so the Telnet server listened whatever the setting said. A module whose block says `enabled: false` (`loginServers.telnet`, `loginServers.ssh`, `contentServers.gopher`, and so on) is now not loaded at all, and the log says so at `info`; the other servers start as usual. SSH and Gopher already checked the setting themselves, so nothing changes for them. See [UPGRADE](UPGRADE.md).

* **Text in a multi-line view narrower than the terminal no longer loses characters** ([#968](https://github.com/NuSkooler/enigma-bbs/issues/968)). Text sent to an `%MT` view was wrapped at the terminal's width but clipped at the view's, so on an 80-column terminal a 73-column view dropped columns 74 to 80 of every wrapped line: the WFC message viewer showed `we can` / `ether` for `we can see whether`. A row that filled the view could also run into the next one when the view did not start at column 1. The WFC message, log and node detail panes, and custom `%MT` info views shown with pipe codes, now word wrap at the view's width. ANSI art (such as file descriptions) is still clipped, not reflowed. Mods can call the view's new `setPipeText()` to get the same for their own text. Word wrapping (here and wherever ENiGMA½ wraps text) breaks long words by the same display width ENiGMA½ uses elsewhere, so a run of wide (e.g. CJK) characters no longer runs past the width or leaves a blank line before it, and a word is no longer cut inside an emoji, flag or accented letter. (In a multi-line view, letters written with combining accents and emoji joined with zero-width joiners can still be laid out wrongly; see [#973](https://github.com/NuSkooler/enigma-bbs/issues/973).) A word with a colour code in it is now kept together like any other word, instead of being broken at the code, which could leave punctuation alone on the next line.

* **Scheduled events can be listed, run on demand, and need no schedule** ([#440](https://github.com/NuSkooler/enigma-bbs/issues/440)). This is the groundwork for running tasks from the WFC. An `eventScheduler.events` entry without a `schedule` is now a manual-only task: listed and runnable on demand, never run on its own (one line at startup names them, so a forgotten `schedule` stays visible). Entries take new, optional members: `desc`, `confirm`, `manual`, `timeout`, and `enabled: false`, which at last lets a board switch off a built-in event. A run that passes its `timeout` is reported as overdue: an `@execute` is killed, while a `@method`, which cannot be stopped, keeps its event blocked until it finishes or an operator abandons it. Every run, whatever started it, now logs its start and its end with how long it took, failures at `warn` (a failing `@method` used to log only at `debug`), and a scheduled run skipped because the last one is still going is logged instead of silently dropped. The last result of each event, including the tail of an `@execute`'s output, is kept across restarts, and new `TaskStarted` / `TaskFinished` system events follow each run.

  Four new built-in tasks, all manual-only until given a schedule: `optimizeDatabases`, `checkpointDatabases` (truncates the WAL files), `backupDatabases` (a consistent copy of the core databases, made while the BBS runs, into `backup/` under `paths.db`, keeping the newest 3) and `tossInboundNow` (asks the FTN BSO tosser to toss its inbound now). For example, `backupDatabases: { schedule: "at 4:00 am" }` backs up nightly. See [Event Scheduler](website/src/content/docs/configuration/event-scheduler.md#built-in-events).

* **Scheduled events follow edits to `config.hjson` without a restart** ([#440](https://github.com/NuSkooler/enigma-bbs/issues/440)). `eventScheduler.events` used to be read once at startup. Now adding, removing, changing or disabling an entry takes effect when the file is saved: new events are armed, removed ones are disarmed (their `@watch` file is no longer watched), changed ones are armed afresh, and the rest are left alone. A run in progress is never interrupted; it finishes under the settings it started with, and an event removed while it runs is dropped once it finishes. An entry that no longer loads is logged and left out without disturbing the others. One log line names what was added, removed and changed, and the WFC task screen updates at once. `@watch` watchers are now also closed at shutdown. See [Event Scheduler](website/src/content/docs/configuration/event-scheduler.md#changing-events-while-running). Also, an `@execute` ended by a signal now records the signal (such as `SIGHUP` when an operator stops it) and no exit code; it used to show exit code 0.

* **The WFC has a task screen** ([#440](https://github.com/NuSkooler/enigma-bbs/issues/440)). <kbd>T</kbd> on the dashboard lists the event scheduler's tasks with their schedule, next run and last result; the detail pane shows the last run in full (duration, error, who ran it, exit code, who stopped it, the tail of its output) and whether it is running or overdue. <kbd>Enter</kbd>/<kbd>R</kbd> runs the selected task, asking first when its entry has `confirm: true`, and <kbd>X</kbd> stops a run after asking: a process is killed, a `@method` is abandoned. Runs go through the scheduler like any other, so the op can go back to the dashboard while one runs, and the screen refreshes every second while a task runs. The activity ticker gains `taskStarted`, `taskFinished`, `taskFailed` and `taskOverdue` (only failures and overruns are shown by default), and a `%SB5` status bar can have a `tasks` panel counting running tasks. Without `wfctasks` art the screen is a plain text list that still runs and stops tasks. See [WFC](website/src/content/docs/modules/wfc.md#tasks).

* **Export FTN mail and pull from BinkP nodes from the WFC** ([#440](https://github.com/NuSkooler/enigma-bbs/issues/440)). Two more built-in manual-only tasks: `exportOutboundNow` asks the FTN BSO scanner/tosser to scan and export new mail now, and `binkpPullNow` runs the native BinkP mailer's pull cycle now, dialing every node `binkp.pullSchedule` would (plus any with mail waiting), with or without a `pullSchedule`. Both finish when the work does and fail if it fails; with FTN not configured they log why and finish without doing anything. A pull cycle already running, from the schedule or by hand, is not started twice, and a node already in a session is still skipped by its `.bsy` lock. The sysop `!BINKP` main menu command is gone: it could never be used (its ACS, `SU`, is not an ACS code, so it was always refused), and it only dialed nodes with mail waiting. The `binkp/binkp_poll_module` menu module it led to now runs the full pull cycle, for custom menus that use it. Also, a scheduled pull on a board with no FTN set up no longer logs at `info` every time it fires. See [Event Scheduler](website/src/content/docs/configuration/event-scheduler.md#built-in-events) and [BinkP](website/src/content/docs/messageareas/binkp.md#pulling-now).

* **Escape in the WFC message viewer no longer leaves the WFC.** The dashboard's keys stayed live under the message viewer and the help page, so escape (or <kbd>Q</kbd> on the help page) also took the op back to the main menu, and the activity ticker kept drawing over both. After a visit to the full log the ticker stopped moving altogether. The dashboard is now set aside while another WFC screen is up and drawn afresh on the way back. The kick-node prompt froze the ticker and the status bar the same way, and stopped the selected node's details following the highlight; that is fixed too, and the kick prompt (like the new task prompt) now starts on *no*, so <kbd>Enter</kbd> alone kicks no one.

* **An upload on one node is no longer deleted when another node finishes its own.** Every upload and every file transfer shared one set of temporary files, and whichever finished first removed them all: another caller's receive directory, with the files still arriving in it, went too, and that upload was lost without an error. Each upload and transfer now has its own and removes only those. The same sharing affected archive extraction during file scans and the QWK and Blue Wave packet readers and writers (two callers building or importing offline mail packets at once); they are fixed too.

* **An upload that is cancelled, fails or is cut off no longer leaves its files behind.** An upload's temporary receive directory, partial files and all, was only removed when the upload completed: backing out at protocol selection, giving up after a failed transfer, disconnecting, or starting another upload left it in the system temp directory. It is now removed on every one of those paths. A disconnect during a transfer waits for the transfer to end first, and a directory the upload did not create itself is never removed. An upload to an area with no storage directory is now logged and discarded; it used to crash the upload. Reloading a menu (a realtime interrupt, or `@systemMethod:reload`) now keeps the menu's `extraArgs`; protocol selection used to crash on one.

* **A file transfer stops when its caller hangs up.** The protocol program (`sz`, `rz`, `sexyz` and the like) was left running after a disconnect until its own timeout, which can be long, writing to nobody, and an upload's temporary receive directory waited for it. It is now sent a hangup the moment the caller disconnects, and `SIGKILL` 5 seconds later if it is still running (on Windows the first kill ends it outright). A door was already killed when its caller hung up. Nothing from an upload cut off this way is credited to the caller, even files its DSZLOG confirms: the caller is gone, so they never reach the file base, and the receive directory is removed once the program has stopped. Also fixed: a protocol program killed by a signal, by anyone, was taken for a clean exit, so a download it never finished was counted and taken off the caller's queue, and an upload credited whatever partial files it left.

* **Reverse proxies are configured in one place, `trustedProxies`** ([#981](https://github.com/NuSkooler/enigma-bbs/issues/981)). The new top-level setting lists the proxies whose `X-Forwarded-For` and `X-Real-IP` headers are believed, as addresses or CIDRs; the default covers loopback and the private ranges, so a proxy on the same host, in another container or on the LAN needs no configuration. With the new `contentServers.web.proxied: true`, the web server uses the forwarded address for its rate limits (REST API login, password reset, 2FA/OTP registration), which behind a proxy are otherwise one limit shared by every visitor, and logs it; the proxy must set `X-Forwarded-For` itself. The WebSocket login server (`proxied: true`) reads the same headers the same way, ignores forwarded headers from any peer not in the list, and no longer takes a multi-hop `X-Forwarded-For` as one address. A WebSocket caller that comes through a proxy is not treated as local. Also fixed: the web server's rate limiter kept an entry for every address it had seen for as long as the process ran. See [Reverse Proxies](website/src/content/docs/servers/contentservers/web-server.md#reverse-proxies) and [UPGRADE](UPGRADE.md).
* **ActivityPub: outbound requests check where a name really points, and an inbox request can only cause so many fetches** ([#966](https://github.com/NuSkooler/enigma-bbs/issues/966)). The board used to check only the name in a URL, so a public name that resolved to a loopback, private or link-local address (or that changed to one after the check) was fetched anyway. Every address a name resolves to is now checked when connecting, and again for each redirect; at most 3 redirects are followed, and a refusal is logged as a warning. Addresses written in a URL are checked better too: IPv4-mapped forms such as `[::ffff:127.0.0.1]` are now refused, and a large public IPv6 range (2a02::/16, among others) that was wrongly refused is now allowed. The fetches an incoming inbox request causes (the sender's actor and key, a forwarded or boosted Note, a handle lookup) are now limited per remote host and board wide, set by the new `outboundFetchLimits` (defaults: 4 at once and 60 a minute per host, 32 at once and 600 a minute in all), and to 16 per request; over the limit the sender is answered `503` with `Retry-After: 60` and delivers again later. Outbound deliveries are not limited. A failed actor or WebFinger lookup is not repeated for 15 minutes, or 2 for a failure that may clear up by itself such as a timeout. `allowInsecureHttp` remains for local development only: it allows `http://` URLs and skips the address checks for them, never for `https://`, and now logs a warning when ActivityPub starts. WebFinger falls back to `http://` only while it is set. The board's own URLs are not checked, so a board behind a reverse proxy whose public name resolves privately on its own host still reaches itself; only its exact scheme, host and port are let through. A fediverse server on your own network is allowed by listing its address or range in the new `allowedPrivateAddresses` (link-local, unspecified, multicast and IPv6 transition addresses can never be allowed). See [ActivityPub Web Handler](website/src/content/docs/servers/contentservers/activitypub-handler.md#outbound-requests-and-limits).

* **ActivityPub: the board signs its own fetches as an instance actor** ([#966](https://github.com/NuSkooler/enigma-bbs/issues/966)). Servers that answer only signed fetches (Mastodon with authorized fetch, and from Mastodon 5.0 for actor documents by default; GoToSocial) refused the fetches the board makes for itself, which went unsigned whenever no local user could sign them: above all the lookup of the actor and key that signed an incoming activity, so activities from such a server could not be checked, and were refused, unless its actor was already cached. These fetches are now signed as the board's instance actor, an `Application` actor at `/_enig/ap/actor` that WebFinger finds as `acct:<domain>@<domain>` and `/.well-known/nodeinfo` links. A fetch a local user signed before (for the inbox the activity came to, or as a local follower) is still signed as that user, and so are deliveries and a user's own searches. The instance actor cannot be followed, has an empty outbox, and its key signs nothing but those fetches. Its key is made at the first start (a failure is logged and tried again a minute later) and kept in `db/activitypub.sqlite3`. A `404` to a fetch signed by the instance actor still does not count as "deleted" for a followers-only Note, since the instance actor follows nobody. A `Delete` of an actor that can no longer be fetched, which the board does not act on because the actor's server does not say it is gone, is now answered `202 Accepted` (and logged, as before) instead of `401`: Mastodon counted the `401` as a failed delivery and sent the same `Delete` again. A local user named exactly like the web domain loses WebFinger to the instance actor; a warning at startup says so. See [Instance Actor](website/src/content/docs/servers/contentservers/activitypub-handler.md#instance-actor).

* **A caller who drops in the first seconds no longer leaves a ghost session** ([#999](https://github.com/NuSkooler/enigma-bbs/issues/999)). A Telnet or WebSocket connection that closed before its terminal type arrived (port scanners and health checks do this) still went on to the menus with nobody there, and then logged an idle timeout kick for that node every minute until the board was restarted. Also: a session that has ended no longer moves to another menu, and a menu that fails to load is not retried forever when the menu before it leads straight back to it with no key pressed (seen with a theme missing both the last callers and pause art); the second failure is logged as an error and the caller is left to the idle timeout. These were busy loops that outlived the caller.

* **Hardening and robustness across the mailer, tosser and web servers.**
  * BinkP: inbound file names are decoded from their FTS-1026 `\xHH` escapes, so a name binkd escaped (one with a space, say) is stored under its real name, and only a plain file name is accepted; a file with any other name is acknowledged without being stored, and logged. A caller giving the wrong password for a node is refused with `Bad password`, as binkd does, and outbound mail is only offered once a caller has authenticated.
  * FTN: a single-valued kludge (`INTL`, `MSGID`, `REPLY`, `CHRS` and so on) that appears more than once keeps its first value, so such a message is imported once and the import carries on. A NetMail with no route is marked failed and its sender told, as intended. Automatic area creation follows the secure inbound (`onDemand.secureInOnly`).
  * TIC: a `Replaces` only ever overwrites the file it supersedes; a payload whose name matches a different existing file is stored beside it.
  * NNTP refuses a password-only login for an account with two-factor authentication. REST refresh tokens and API keys require an active account, and are revoked when `oputil` disables, locks or deactivates one.
  * Web and REST request bodies are read with size limits (HTTP 413 beyond them), and multi-byte characters in REST message bodies arrive intact.
  * ActivityPub: inbound signed requests must sign `(request-target)`, `host`, `date` and, on a POST, a matching `Digest`. A thread's `/note/context` collection is indexed and paged beyond 100 Notes, and the NodeInfo usage counts are cached for 10 minutes.

* **FTN import and export do less work per message.** Looking up a message by a meta value, which the tosser does for every imported message (the MSGID duplicate check, resolving `REPLY`), used to read through the whole `message_meta` table; a new index makes it a direct lookup (about 50 ms down to a few microseconds on a board with 36,000 messages). EchoMail export now loads each message, looks up its `REPLY` and records it as exported once, however many uplinks it goes to, where it used to do all of that once per uplink; EchoMail relay does the same across all the destinations of a network. On that board, relaying 4,983 messages to three destinations went from about 21 to about 16 seconds. What each uplink receives is unchanged.

* **The WFC node list keeps the node the sysop selected.** Moving the highlight with the arrow or page keys was undone at the next five-second refresh, which put it back on the node picked last with a node number (or the first); kick, chat and message act on the highlighted node, so for a few seconds they targeted one node and then another. The selection now follows the node, not its row: the arrow keys and node-number keys both set it, a refresh never moves it, and it stays on the same node when other nodes connect or disconnect. If the selected node disconnects, the first node is selected. A kick now goes to the caller shown when the confirm prompt opened: if that caller hangs up before the sysop answers, nobody is kicked, where before it could hit whichever node was highlighted, or had that node number, by then.

* **Art goes to the caller in one write.** Each escape sequence and run of text in a piece of art used to be its own socket write, so one 80x25 screen went out as several hundred TCP segments, SSH messages or WebSocket frames (607 to 823 for screens in the stock theme). It is now sent as one, and so is a form redrawn in full, as is the WFC's periodic refresh. What the caller receives is byte for byte the same for ANSI, PETSCII, ATASCII and RIP callers, and art shown with `baudRate` is paced exactly as before.

* **Screens refreshed on a timer draw only what changed.** The WFC dashboard repainted every custom view and the whole node list every five seconds, changed or not: about 2,200 bytes a refresh on an idle dashboard with four nodes connected. It now draws only the values that changed, so an idle refresh is down to the status bar (about 450 bytes). The node list is drawn again when what it shows or its selection changes, not for a field it does not show, and the node list and quick log no longer blank their rows before redrawing the same number of them, which made them flicker. The task screen's custom views, MRC's custom views and sysop chat's status line work the same way. A chat line added to the MRC or sysop chat log goes out as one write instead of one per row, and until the log fills and starts to scroll only the new line is drawn: about 175 bytes a line instead of up to 2,500 in MRC. What the caller sees is unchanged.

* **EchoMail export retries an uplink that failed** ([#1026](https://github.com/NuSkooler/enigma-bbs/issues/1026)). A message is marked exported as soon as it is handed to its first uplink, before any packet is moved into outbound. If anything after that failed (a full disk, a permission error, a flow file busy with a mailer session, or one uplink of several being unreachable), the log said "will retry", but the export scan never selected that message again, so the uplink that missed it never got it. Each message now records which uplinks are still owed it until the packet carrying it is in that uplink's outbound and referenced from its flow file, and the next scan sends it to those uplinks only, with the same MSGID. A packet that got out is not sent again, even when a later packet to the same uplink failed (a bundle goes out whole or not at all). A duplicate is still possible if ENiGMA½ stops between a packet reaching outbound and that being recorded, or if recording it fails (logged at `error`); the receiving tosser drops it by MSGID. A live (`@immediate`) export that fails for an uplink is retried the same way. Which messages are exported, and what a successful export sends, are unchanged. EchoMail relay already retried per uplink and is unchanged.

* **EchoMail from several areas to one uplink no longer shares a bundle name** ([#1027](https://github.com/NuSkooler/enigma-bbs/issues/1027)). The export scan exports its areas at the same time, and each picked its ArcMail bundle name by looking at what was already in the uplink's outbound. Two areas with new mail for the same uplink (with `archiveType` set) could pick the same name before either bundle existed. The archiver then added one area's packets to the other's bundle, or, with both running at once, kept only one of them: the second area's export failed and its mail was sent again on the next scan, and the first area's mail could be recorded as sent when its bundle held only the other area's packets. A bundle name is now reserved while its bundle is built and moved into outbound, so every export running in the same ENiGMA½ process gets its own. A name already in outbound in upper case (`.TU0`) is passed over too. A bundle that does not reach outbound is removed from the export temp directory; before, the next bundle given that name was added to it and sent the old packets again. The day-of-week naming (`.mo0` to `.moz`, 36 bundles per uplink per day) is unchanged. The packets that went into a bundle are now removed from the export temp directory once the bundle is in outbound; they used to stay there until ENiGMA½ stopped.

* **A NetMail addressed only to our FTN address no longer stalls the import.** Such a NetMail, with no local user of that name, is meant for the SysOp. It was never stored, and the packet import it was in never finished.

## 0.5.1-beta

* **The file base can read ARC, PAK, ZOO, ACE, Squeeze It, UltraCompressor II, Unix `.Z`, xz, Zstandard and Microsoft Cabinet archives, C64 Lynx, T64 and D64 files, and the files on Amiga DMS disks** -- with [unarc](https://github.com/mkrueger/unarc-rs) installed. Uploads in these formats were treated as plain files, so nothing inside them was listed or used for a description. unarc is a single program that reads most archive formats found on BBSes; ENiGMA½ now lists their contents and takes descriptions from a `FILE_ID.DIZ` or `README` inside, as it does for ZIP. A DMS disk's attached `FILE_ID.DIZ` becomes its description. unarc is **not** shipped with ENiGMA½, and nothing changes until it is installed.

  * **New boards:** install unarc (see [Archivers](website/src/content/docs/configuration/archivers.md#unarc)) and it covers most archive types on its own, including Amiga LZX and Atari ATR in place of `unlzx` and `atr` -- point those two archivers at it as the Archivers page shows.
  * **Existing boards:** nothing breaks. LZX and ATR keep using `unlzx` and `atr`, and DMS keeps its `xdms` description until unarc can list it. Migrating is optional; see [UPGRADE](UPGRADE.md).

  Also: plain `.tar` files and LHA archives made by LArc (`-lz4-`, `-lz5-`) are recognised and handled by `tar` and `lha`. Lynx and D64 have no fixed signature, so they are recognised by extension once no signature matches. An upload whose archiver cannot list it -- a misnamed or damaged file, or a missing archiver -- is now handled as a plain file instead of being kept as an archive with an empty listing. And an Amiga `.info` icon is no longer taken for an `.NFO` and used as a long description.

* **REST API logout now receives and revokes the browser's refresh token.** The refresh cookie previously used a path restricted to `/auth/refresh`, so browsers did not send it to the sibling `/auth/logout` route. Login and refresh now issue the cookie at `/auth`, retain `HttpOnly`, `Secure` and `SameSite=Strict`, and expire the legacy cookie. Logout clears both cookie paths. Existing sessions migrate on their next successful refresh or login; already-issued access tokens still expire after their normal 15-minute lifetime. See [UPGRADE](UPGRADE.md).

* **Blue Wave readers can now choose a caller's areas offline** ([#883](https://github.com/NuSkooler/enigma-bbs/issues/883)), **and an offline mail upload says where each message went** ([#882](https://github.com/NuSkooler/enigma-bbs/issues/882)). A Blue Wave reader lets the caller turn areas on and off, and sends the result back in the reply packet as a `*.OLC` (or a `*.PDQ` from an older reader). ENiGMA½ used to unpack that file and ignore it. Callers who unsubscribed from echoes in their reader kept getting them, and nothing told them why.

  The file is now applied. It is the caller's whole list of areas rather than a set of changes, as the Blue Wave door treated it, so an area left off the list leaves their packet. An area turned on starts from the upload rather than from the area's whole history. Only areas the caller can see can be turned on; any other is refused and named. A list that would leave no areas at all is not applied, because a caller with nothing selected would never get another packet to undo it from.

  The packet now lists every area the caller can read, with the ones they have not selected unflagged, so a reader can offer to turn them back on. It used to list only the selected areas, which, once drops took effect, would have left a dropped area with no way back.

  After an upload of either format, QWK or Blue Wave, the caller now sees a line per area with its count, where they used to see only `Imported 1 message(s)`. Any area changes follow (`Added to packet: FIDO_TECH`, `Removed from packet: FIDO_GENERAL`, `Not available here: ...`). See [Choosing Areas Offline](website/src/content/docs/messageareas/bluewave.md#choosing-areas-offline).

* **Security: a door's socket server no longer listens on every interface** ([#885](https://github.com/NuSkooler/enigma-bbs/issues/885)). With `io: socket`, ENiGMA½ stands up a temporary TCP server for the door -- or for the emulator bridging the door's COM port -- to connect back to, and pipes the caller's session to the first connection that arrives. That server was started with no address, so Node bound the unspecified address: every interface on a dual-stack machine. Anyone who could reach the box and connect before the door did received the caller's keystrokes and could write to their terminal, with no authentication anywhere in it, and the door itself then got nothing. The window is however long the door or emulator takes to start -- seconds, for DOSEMU, QEMU or DOSBox -- and while the port is ephemeral, scanning a range is cheap.

  The server now binds `127.0.0.1`. `io: stdio` doors never had a server and were never affected.

  **A launch script or emulator pointed at the machine's LAN address will stop connecting** -- point it at `127.0.0.1`, spelled that way rather than `localhost`, which can resolve to `::1` and miss the listener. The rare setup whose emulator or bridge really is on another machine can say so with a new per-door `socketBindAddress`, which is honoured but logged as a warning every time that door starts. Loopback still means any local process, so the account ENiGMA½ runs as should own the door's scripts and binaries. See [UPGRADE](UPGRADE.md) and [Scripts & Native Binaries](website/src/content/docs/doors/scripts-and-binaries.md).

* **Doors now run at the caller's pace.** A door that writes faster than its caller can take it in — a sixel game, a terminal slow to render, a slow link — used to have every byte queued in ENiGMA½'s memory, with nothing to stop it. The caller fell further and further behind until the door looked frozen, while the backlog grew without limit. A test door flooding a caller who drains 100 KB/s piled up over 500 MB in six seconds.

  ENiGMA½ now stops reading a door's output while too much is waiting to be sent to the caller, and starts again once they have caught up. The door's own writes block in the meantime, so it simply runs at the caller's speed. Input is never held back. It is on by default, applies to `io: stdio` and `io: socket` doors alike, and only engages when a caller is actually behind. See `doors.outputBackpressure` in [Scripts & Native Binaries](website/src/content/docs/doors/scripts-and-binaries.md) to tune or disable it.

* **SEXYZ file transfers now work over SSH** ([#353](https://github.com/NuSkooler/enigma-bbs/issues/353)). Any transfer using a SEXYZ protocol — including **ZModem 8k (SEXYZ)**, the default on x86-64 — failed for callers connected over SSH. The transfer simply never started, with nothing in the log to explain it.

  `sexyz` takes its transport from its command line: `-telnet` turns Telnet IAC escaping on, `-ssh` turns it off. ENiGMA½ passed `-telnet` to every caller, so over SSH `sexyz` escaped `0xFF` bytes onto a connection with no Telnet layer to unescape them. The flag is now chosen from how the caller actually connected. Nothing to configure — this applies to customised protocol definitions too, so a board that copied the shipped argument lists is fixed by upgrading.

  Confirmed against SyncTERM, NetRunner, IcyTerm and TERMinator, with matching SHA-256 sums before and after.

* **File transfers through the Telnet bridge now work over SSH** ([#266](https://github.com/NuSkooler/enigma-bbs/issues/266)). Downloading from a remote board reached via `telnet_bridge` failed a few chunks in with `recv_header timeout` if you had connected to ENiGMA½ over SSH, while the same download over Telnet was fine.

  The bridge piped bytes between the two sides untouched. That is correct for a Telnet or WebSocket caller, whose own client speaks Telnet and undoes the escaping itself — but an SSH caller has no Telnet layer, so the remote's doubled `0xFF` bytes arrived doubled and its negotiation landed in the middle of the download. The bridge now terminates Telnet itself for those callers: it de-escapes the data, keeps negotiation out of the stream, and answers that negotiation on the caller's behalf. Telnet and WebSocket callers are unchanged.

* **Large and binary uploads no longer corrupt on Telnet and WebSocket connections.** An escaped `0xFF` pair split across two reads was not recognised as a pair, so both bytes reached `sz`/`rz` and the transfer failed. Small files often contained no `0xFF` at all and were unaffected, which is why this showed up as "works for small files, fails at 12MB+". Images were worst hit — JPEG is saturated with `0xFF`.

* **Exodus has shut down; the module (`exodus.js`) has been removed** ([#857](https://github.com/NuSkooler/enigma-bbs/issues/857)). Both ports the module needs refuse connections and every documented URL is gone, so there was nothing left to point it at. See [UPGRADE](UPGRADE.md) if your `menu.hjson` still carries an Exodus menu.

* **Daily time limits** ([#795](https://github.com/NuSkooler/enigma-bbs/issues/795)) — ENiGMA½ can now meter how long a user spends on the board each day and cut them off when their allowance runs out.

  **Nothing is metered until you say so.** No allowance ships configured, every user is unlimited, and upgrading an existing board changes nothing. Time used today is tracked regardless, so `oputil.js user info` and the new `TD` MCI code tell the truth even where nothing is enforced — it is the "time on today" figure ENiGMA½ has never had.

  An allowance is a `users.timeLimits` band: an ordered list where the first entry whose `acs` matches wins, and an entry with no `acs` at all is the default. A per-account override beats every band, set with `oputil.js user time USERNAME <minutes|clear>`.

  ```hjson
  users: {
      timeLimits: [
          { acs: GM[vip], minutesPerDay: 240 }
          { acs: GM[users], minutesPerDay: 90 }
          { minutesPerDay: 30 }
      ]
  }
  ```

  The root user and anyone in the `sysops` group are exempt, in code, and cannot be metered.

  The `ML` ACS code — a `:TODO: implement me!` stub since 2015 — now means "at least *n* minutes left", so `acs: ML15` keeps a user out of a door they have no time for. It is **true whenever no budget applies**, including where ACS is evaluated with no session at all, so it cannot silently hide a message area over NNTP or the web API on a board that has not opted in. Art gets `TR` (remaining), `TA` (allowed today) and `TD` (used today) for `{TD} / {TA}`-style displays.

  Users are warned at 5, 3, 2 and 1 minutes, then sent to a new `timeUpLogoff` menu; if its art does not exist they get a plain message rather than a silent drop. Someone whose allowance is already spent is turned away at login rather than let in for a minute first. A door can be given `minTimeLeftMinutes`, which refuses to *start* it when there is not enough time rather than killing it part way through.

  See [Time Limits](https://enigma-bbs.github.io/configuration/time-limits/).

* **Doors are told how much time the caller actually has** ([#795](https://github.com/NuSkooler/enigma-bbs/issues/795)) — `DOOR.SYS` lines 18 and 19, `DOOR32.SYS` line 9 and `DORINFO1.DEF` line 12 carried fixed placeholders: `15360`, `256` and `546`. The `256`s came from x/84 and mean nothing; `546` is real, but it is the documented *ceiling* a value must be clamped to, not a sentinel meaning "unlimited", so we had been using it backwards.

  Each now states the minutes actually left today, capped at 546 — `546 × 60 = 32760`, which fits a signed 16-bit integer, so a door converting minutes to seconds cannot overflow. The seconds field is derived from the same clamped minutes, so the two can never disagree. A caller with no limit is told the ceiling like any other large number.

  `DOOR.SYS` line 42, "time credits", now reads `0`. The GAP spec has doors read it back and ENiGMA½ has no time bank, so any other value was a claim it could not honour. `BBSDEV.DRP` line 11 states the logoff deadline as an absolute UTC instant, and stays empty where nothing will end the session.

* **DOOR.SYS reports distinct call times** ([#824](https://github.com/NuSkooler/enigma-bbs/issues/824)) — the current and previous login times now occupy their respective fields in 24-hour format. First-time callers leave the previous-call field blank instead of repeating the current time.

* **Post from a message list** ([#213](https://github.com/NuSkooler/enigma-bbs/issues/213)) — <kbd>P</kbd> on the message list, or the personal message list, starts a new message where before you had to back out to the message menu to reach its own <kbd>P</kbd>. The post goes to the area the highlighted message is in, so it does the right thing on a list that spans areas. An existing board keeps the menus it has, so see [UPGRADE.md](UPGRADE.md) for the binding to add.

* **Doors can be handed a [`BBSDEV.DRP`](https://github.com/RealDeuce/bbsdev.drp) drop file** — set `dropFileType: BBSDEV` on an `abracadabra` door. The older formats are CP437, so a user whose name ENiGMA½ stores fine reaches the door mangled, and they leave the terminal's character set, the caller's language and the meaning of the comm field to convention. The new format is UTF-8 and states all three.

  The door is told where the file is through the `BBSDEV_DRP` environment variable rather than an argument, so nothing has to be quoted or escaped through a shell. `commType` accepts the mechanisms ENiGMA½ can honestly name — `local`, `stdio`, `serial`, `winserial`, `uart` and `fossil` — with the descriptor, handle, UART base or FOSSIL port in a new `commParams`. A channel ENiGMA½ cannot name stops the door from starting, with the reason logged, rather than writing a `local` that is untrue: that is the format's own rule, and `io: socket` is where it bites, since the format's socket is one the door inherits rather than one it dials.

  `general.language` sets the BCP 47 tag reported to doors, `en-US` by default. SyncTERM and other CTerm terminals now have their revision recorded from the Device Attributes reply they were already sending, which the drop file passes on.

* **Blue Wave offline mail packets** ([#119](https://github.com/NuSkooler/enigma-bbs/issues/119)) — a caller can export their unread messages as a Blue Wave packet and read them offline. Where QWK identifies a message area by a conference number, Blue Wave carries a 20 character echotag, so a reply is routed by a name that survives the sysop renumbering the message base.

  The new `message_base_bluewave_export` menu module writes the packet and places it in the caller's download queue, area by area from the point each was last exported. `messageNetworks.bluewave` sets the packet ID and pins an area's echotag, number or title where the derived one will not do. Callers reach it with <kbd>B</kbd> from the message base menu, and <kbd>E</kbd> takes them to the download manager to fetch what it queued, without a detour through the file base. See [Blue Wave Support](https://enigma-bbs.github.io/messageareas/bluewave/).

  Replies written offline come back in ([#810](https://github.com/NuSkooler/enigma-bbs/issues/810)). The new `message_base_offline_import` menu module takes the uploaded reply packet, reached with <kbd>U</kbd> from the message base menu. A packet advertises that it takes replies only when one of your menus carries that module. Nothing asks the caller what format it is: a reply packet names itself from the inside, so the archive is opened and read by whichever reader matches, and the format is chosen on the way out rather than on the way back.

  Each reply is placed by echotag and then checked as though the caller had typed it at the keyboard -- write access on the target area, a real user for personal mail, and the `From` name replaced with their own, since a reader writes whatever name it was configured with. A packet built for a different login is refused. A reply is threaded onto the message it answers, which the packet names by that message's own ID.

  The same entry takes a QWK `*.REP` packet. The QWK reader's reply mode had never worked: it required a `CONTROL.DAT`, which a reply packet does not carry, and looked for a messages file under a fixed name rather than the one named for the host. Both are fixed, so QWK mail is now two-way as well.

* **`oputil.js config validate` checks your configuration before you restart** ([#281](https://github.com/NuSkooler/enigma-bbs/issues/281)) — a mistyped key in `config.hjson` has never been reported. Because your file is merged *into* the defaults, a typo does not replace anything: `outbund` lands quietly beside `outbound`, the setting you wrote is never read, and the board goes on using the default. Nothing is logged, and the file looks correct.

  The new command reports those, along with values whose type disagrees with the default they override:

  ```
  config.hjson: 2 issues (1 error, 1 warning)

    error    general.maxConnections
             expected number, got string

    warning  scannerTossers.ftn_bso.paths.outbund
             unknown key "outbund" -- did you mean "outbound"?
  ```

  It exits non-zero when there are errors, so it can be used from a script or a systemd `ExecStartPre`. Warnings alone are not a failure: an unrecognised key may perfectly well belong to a mod. Sections you add yourself, and the tags and names you choose for areas, networks and nodes, are never reported.

  `--check-env` additionally reports `@environment:`, `@file:` and `@reference:` specs that do not resolve. That one is opt-in because resolution depends on the shell it runs in: checked by default, a perfectly good configuration would look broken purely because it was validated from the wrong place.

  It also checks names that have to line up across sections — a file area naming a storage tag that was renamed, a `ticAreas` entry pointing at a file area that does not exist, an echo or a NetMail route naming a network spelled differently where it is defined, an NNTP conference or area exposed publicly that is not there. None of those produce an error today: the file quietly never lands, the echo is quietly never exported, and nothing in the log says why.

  **A theme or a first menu that is not there is now reported too.** `theme.default`, `theme.preLogin` and each login server's `firstMenu` name things that live outside `config.hjson` — a directory under `paths.themes`, an entry in `menu.hjson` — so until now the only way to find a typo in one was to restart and watch what happened. A misnamed theme quietly falls back to whichever theme loads first; a misnamed first menu breaks that login server for everyone using it.

  ```
    error    theme.default
             theme "lucian_blocktronics" is not defined in paths.themes -- did you mean "luciano_blocktronics"?
  ```

  Checked at startup, once the themes and menus are loaded, and by `oputil.js config validate` — which gathers both sets itself, so it can tell you before the restart rather than after. `*` still means "pick one at random" and is left alone, and a login server you have switched off is not checked at all, since a menu for a server nobody can reach is not a problem. If either set cannot be read, nothing is reported rather than everything.

  **Values are now checked, not just key names.** A port outside 1-65535, a `logging.rotatingFile.level` bunyan has never heard of, a negative idle timeout, a two factor method that is not implemented, a TIC `fileCase` that is neither `lower` nor `upper` — each of these is reported with the values that would have worked. Every one of them was taken from the code that reads the setting, and a test asserts that no constraint excludes the value ENiGMA½ itself ships, because a validator that fails a correct board is worse than none.

  **`achievements.hjson` is checked too** — at startup, on reload, and by `oputil.js config validate`, which now reports on both files and names each one. A `statname` written for `statName` has always meant the achievement is silently discarded at load and simply never fires, with nothing logged either way. The same goes for a `type` that is not one of the three the code implements, or a tier whose `points` are a string. An `achievements.hjson` that cannot be read at all is reported as a warning rather than a failure, because that is what the board itself does: it logs and carries on without achievements.

  Checking it turned up one more defect: **art and date formats set on an *achievement* were silently ignored.** They are meant to be overridable at three levels — the tier, the achievement, then the file's top level — but the middle one read the wrong object and so never matched. Tier-level and file-level overrides worked; the one in between did nothing.

  **`menu.hjson` and your themes are checked too.** They carry the same silent failure as `config.hjson`, and one of them is worse: `ThemeManager` starts from your menu file and looks each menu up in the theme, so a `customization` naming a menu that does not exist is **never consulted** — the theming simply does not happen, with nothing logged. The theme ENiGMA½ ships had eight such blocks; they are fixed, and a check now reports any that remain as a warning.

  **A menu naming a module that cannot be loaded is reported too**, for both built-in modules and your own under `paths.mods`. That found the sysop `!BINKP` command pointing at `binkp_poll`, which has never existed — the module is `binkp/binkp_poll_module` — so the command has failed since native BinkP support landed.

  Menu files get their structure checked — a misspelled `modul` for `module`, an `acs` where only `config.acs` is read — along with every menu name they reference, wherever it appears: `next`, a submit handler, an action key. That last one immediately found the `S` command in the ActivityPub menu pointing at a menu that has never existed.

  `config{}`, `form{}` and MCI blocks are deliberately **not** checked: those belong to the modules that read them and to the art they position, and claiming to know them would report most menus on most boards.

  A machine-readable **[JSON Schema](https://json-schema.org/) for `config.hjson` is now published** at `misc/config.schema.json`, generated from the same source the validator uses by `npm run build:schema`. It is there for the configuration editor asked for in [#133](https://github.com/NuSkooler/enigma-bbs/issues/133) and for anything else that wants to know what a setting is called, what type it takes and what it defaults to, without reading `config_default.js`. A test fails if it is ever out of date. Note it describes the configuration *after* `@reference:`, `@environment:` and `@file:` specs are resolved, and that HJSON editors do not consume JSON Schema — this is not editor tooling.

  Writing it turned up a false positive in the validator itself: **an archiver or file transfer protocol of your own could be told a legitimate key was a typo.** The shapes of those blocks are inferred from the examples ENiGMA½ ships, and only the outermost level of an inferred shape was left open. So `entryGroupOrder` — which the shipped `Arj` archiver uses, but the first archiver in the list does not — was reported as an unknown key inside anyone else's `list{}`, as was `processIACs` inside a custom protocol's `external{}`. Inferred shapes are now open at every level.

  The same problems are now also reported **at startup and when you edit a running board** — on the console at startup, since the log is not open yet, and to the log on a hot reload. Neither ever stops anything: a configuration with problems is still applied, exactly as before. Set `general.configValidation` to `off` to stay silent; `oputil.js config validate` keeps working either way. There is deliberately no strict mode.

* **Notifications reach an +op at the WFC without wrecking the dashboard** ([#438](https://github.com/NuSkooler/enigma-bbs/issues/438), [#217](https://github.com/NuSkooler/enigma-bbs/issues/217)) — an +op sitting at the waiting-for-caller screen is a node like any other, so achievements, node messages and time warnings were all aimed at their terminal. The WFC queues rather than displays, so nothing appeared at the time; the items were then flushed on the way *out*, painting over whatever menu the op had moved to. A dashboard that gets painted over is not a dashboard, so nothing is drawn on top of it any more — each notification is **routed** instead.

  Every interrupt item now carries a `type` (`nodeMsg`, `achievement`, `achievementGlobal`, `sysopPage`, `timeWarning`, `system`) and, where a person is involved, a `from` naming them. Each type is routed to zero or more *sinks*:

  | Type | Default sinks | Why |
  |---|---|---|
  | `nodeMsg` | `inbox`, `statusBar` | read on the op's terms |
  | `achievement` / `achievementGlobal` | `log` | decorative; the shipped `achievements.hjson` has 125 `globalText` entries |
  | `sysopPage` | *(none)* | `pendingPages` and the node-list indicator already show it |
  | `timeWarning` | *(none)* | sysops are typically unlimited |
  | `system` / untagged | `interrupt` | anything unforeseen behaves exactly as before |

  An untagged item is `system` and therefore still interrupts, so nothing a third-party module queues can be silently swallowed. Override any of it per install with a `notifications` block on the menu.

  <kbd>M</kbd> opens a message viewer (<kbd>R</kbd> reply, <kbd>D</kbd>/<kbd>DEL</kbd> dismiss), and <kbd>S</kbd> sends to the node highlighted in the node list — #438's "select a node and send". Both go to a new `wfcNodeMessage` menu rather than the `nodeMessage` users reach with `msg`: the same module and art, but its own entry, so the sysop path can be rethemed without changing what callers see. The inbox hangs off the connection rather than the module instance, because leaving the WFC destroys and rebuilds that instance — an inbox on it would lose anything unread the moment the op stepped away.

  Earning an achievement produced **no** `Log` call anywhere, so it was invisible in the rotating log and both WFC log views. It is logged now, which is what makes the `log` sink mean anything.

  An existing board keeps the menus it has, so see [UPGRADE.md](UPGRADE.md) for the keys and menu entry to add.

  See [WFC](https://enigma-bbs.github.io/modules/wfc/).

* **Four bugs behind "the WFC gets corrupted when another node earns an achievement"** — the framing turned out to be wrong: an achievement arriving while an +op sits at the WFC writes **zero** bytes at the time. The corruption came from four separate defects, each now with a targeted test.

  * **The WFC leaked its `ClientDisconnected` listener.** `enter()` registered a bound function and `leave()` removed a *freshly* bound one, which never matches — one listener per visit. Since `View.destroy()` is a no-op, those stale instances kept running their refresh and painting the node list, quick log and stat views over whatever menu the op had since moved to. Reproducible on an unrelated telnet client dropping.
  * **The interrupt queue was flushed while the outgoing menu was still live**, so a refresh timer was still repainting over the interrupt art and the key that dismissed it also reached the departing menu's action keys — where <kbd>K</kbd> opens the kick-node confirm.
  * **The queue was LIFO**, so a run of node messages was read newest-first.
  * **Two +ops collided over the quick log.** Each WFC instance added a bunyan stream under the same name, and `leave()` removed streams *by* that name — so the first op to leave silently and permanently froze the other's quick log, with nothing on screen to say so.

  `sysop_chat` had the second of those in its own exit path and now holds interrupts for the destination menu instead.

* **Queued interrupts are drained on arrival only** — the queue was drained at four sites: once on arrival, and three times on *departure*, in `prevMenu()`, `nextMenu()` and `autoNextMenu()`. The departure drains are the defect above, and they ran before the outgoing menu's `leave()`, so its form was still bound to key presses while the interrupt waited for one.

  Draining now happens only on arrival, where the destination owns the screen and nothing is attached. This is **more** coverage than before, not less: 29 modules override `initSequence()` without draining, so a queued item was never shown while inside any of them; the drain moved to `enter()`, which only four modules override and all four call `super`. A module that must not be interrupted while arriving overrides `displayQueuedInterruptions()` or sets `interrupt: never`.

* **A WFC activity ticker** — add a `%TK6` ticker to the WFC art and it becomes a board activity marquee, fed from the same nine system events that already drive each user's log: if it is worth writing to a user's log it is worth putting on the marquee. `userLogin`, `userAchievementEarned` and `userUpload` have default formats and the rest are opt-in, since an event with no format string is not shown. `ticker.rotateOn` takes `"cycle"` or a number of milliseconds, and `ticker.idleText` covers a dry feed so the row is never blank. Routing a notification type to the `ticker` sink puts it on the marquee too. Alongside it, `%SB5` became a real status bar: any named panel is filled from `statusBar<Name>Format` against the dashboard's values (now including `{boardName}`), and `statusBar<Name>ActiveFormat` lights the unread message and page counts while they are non-zero.

  `TickerView` gained a **`cycle complete`** event for this, emitted at each motion's natural boundary — when a scroll offset wraps, when a hold phase ends, when a bounce completes its round trip. A feed that swaps text on that event never cuts a message off mid-word, which a plain timer would. Useful to anything driving a ticker, not only the WFC.

* **`opVisibility` accepts the booleans it was always documented as taking** — `wfc.md` has described a boolean since the option existed while the code matched only `'hidden'` and `'visible'`, so `opVisibility: false` fell through the switch and did nothing. That is the form people wrote. It matters because an invisible +op is excluded from `getActiveConnections({visibleOnly: true})` and therefore receives no broadcast notifications at all. Strings stay canonical; **this changes behaviour on an existing board**, so see [UPGRADE.md](UPGRADE.md).

* **TIC-announced files were lost whenever the file arrived after its announcement** ([#735](https://github.com/NuSkooler/enigma-bbs/issues/735)) — a `.tic` control file and the file it announces routinely arrive in *separate* mailer sessions; a peer running HTick was observed announcing a full Zone 1 nodelist 15–20 minutes ahead of the payload. ENiGMA½ processed the `.tic` the moment it landed, could not find the file, archived the announcement to `reject/` and unlinked it. The file then arrived with nothing left to pair it with and sat in the secure inbound indefinitely. For that peer and that file it failed every single time, and recovery meant finding the orphan by hand and forcing a rescan.

  A TIC whose file is not here yet is now **held** and retried on later import passes — the same disposition HTick uses (`TIC_NotRecvd`, "has not been received, waiting") — rather than rejected. Because an import pass already runs the instant a BinkP session delivers files, the pairing normally completes within seconds of the file landing. A TIC that is never satisfied is given up on after `tic.holdMaxAgeMs` (48 hours by default) and rejected as before, so nothing accumulates forever.

  Four more defects in the same code path came out with it:

  * **The announced name was matched case-sensitively.** A TIC naming `NODELIST.Z34` never found a delivered `nodelist.z34`. Other FTN software normalises this (HTick calls `adaptcase()`); ENiGMA½ now resolves the name case-insensitively against the inbound.

  * **A file still being written could be deleted.** A payload shorter than the TIC's `Size`, or one failing its CRC, was archived as a reject and unlinked — which, with a mailer that writes directly into the inbound, could destroy a transfer in progress. Short and mismatched payloads are now held and re-checked instead.

  * **A `.tic` with no `File` field crashed the import pass.** Building the payload path threw a `TypeError` that escaped into a filesystem callback, leaving the pass hung until the five-minute watchdog fired — so every remaining TIC, and the other inbound directory, were skipped. Such a TIC is now simply rejected and the pass continues.

  * **`tic.secureInOnly` did nothing.** Documented and defaulted to `true` since TIC support landed, it was never read, so TIC files in the *unsecure* inbound were imported on the strength of an unauthenticated `From` line. It is now enforced. See [UPGRADE](UPGRADE.md) if you relied on the old behaviour.

* **A TIC could write its file anywhere the BBS user could write** ([#735](https://github.com/NuSkooler/enigma-bbs/issues/735)) — the `File` field was checked for path traversal, but `Lfile`/`Fullname` were not, and it is the *long* name a file is stored under: `paths.join(areaStorageDir, ticFileInfo.longFileName)`. A peer whose TIC otherwise validated could therefore send `Lfile ../../../somewhere/evil` and place arbitrary content outside the file base. All three fields are now checked, and `longFileName` discards an unsafe candidate rather than returning it. Found by a security review of the work above and confirmed against a live instance.

  Two smaller things fall out of the same work: the TIC password is now compared without regard to case, as other FTN software does and as ENiGMA½ already did for packet passwords; and the packet and bundle import stages, which run over the same directory first, no longer consume a TIC-announced file whose name happens to match their patterns.

* **Two more ways a TIC file could hurt you, both found by fuzzing the parser** ([#743](https://github.com/NuSkooler/enigma-bbs/issues/743)) — the same shape as the traversal above, reachable again by different routes.

  * **A single NUL byte in the `File` field stalled the entire import pass.** A name like `NODE<NUL>LIST.Z21` is not a path separator, is not `..` and is not absolute, so every safety check passed it — and the filesystem call that followed threw *synchronously*, escaping the asynchronous machinery so the import never finished. Every remaining TIC and the other inbound directory were skipped until the five-minute watchdog fired. Control characters are now rejected in an announced file name.

  * **A TIC could cause an arbitrary file to be copied and then deleted.** The path of the announced file was built without a safety check, so `File ../../../etc/passwd` resolved outside the inbound. Such a TIC is rejected — but *rejecting* is what does the damage: the reject path archives the announced file to `paths.reject` and then unlinks it. This needed neither a known node nor an area you carry, because the `File` field is read several steps before those checks.

  Nine further robustness defects came out of the same work, none individually dramatic: a legal 2-dimensional `Seenby` was written back as `undefined:1/50` to every downlink; a peer's `Seenby` list of a few thousand entries could stall the event loop for seconds; a `Crc` of `00000000` — the checksum of an empty file — was misread as a *missing* field and the TIC rejected; and a bare CR inside a value could smuggle an extra keyword line into TICs forwarded under your own name.

* **NetMail could not be sent to a node you had configured, without also adding a route for it** ([#739](https://github.com/NuSkooler/enigma-bbs/issues/739)) — `netMail.routes` is meant to say where mail goes when it is *not* going direct, but in practice it was mandatory for every NetMail destination. A message to an uplink sitting right there in `nodes{}` was refused with `No NetMail route for …`, and the sender got a delivery failure notice.

  The network was being resolved with a helper that compares an address against your own `localAddress` — the right question when *importing* a packet addressed to you, and one a correspondent can never answer yes to. So the unrouted path could only ever succeed for mail addressed to yourself.

  Destinations are now settled as the code always described: a `routes` entry if one matches, otherwise a `nodes` entry for the recipient itself, otherwise refused. Nothing that worked before changes — routes are still consulted first and handled exactly as they were.

  Two smaller things fall out of the same rework:

  * **`network` is now optional on a route.** Omitting it used to produce the same `No NetMail route` error even though a route had matched. It is filled in from the zone of the node being dialed, which is what picks the outbound directory anyway, so the from-address and the spool path cannot disagree. Name a `network` — on a route or on a `nodes` entry — only when two of your networks share a zone.

  * **Bad configuration is reported for what it is.** A route naming a network that does not exist, or carrying an address that will not parse, now says so. The first was reported a step later as a problem with the network rather than the route; the second threw.

  This also means automatic AreaFix rescan requests ([#241](https://github.com/NuSkooler/enigma-bbs/issues/241)) reach an uplink without a `routes` entry having to cover it.

* **Routed cross-zone NetMail was filed where nothing would ever look for it** ([#734](https://github.com/NuSkooler/enigma-bbs/issues/734)) -- NetMail routed through an uplink in a different zone than the recipient (the standard FidoNet zone gate: zone 2 mail leaving through a zone 1 hub) was written to the outbound directory of the *recipient's* zone instead of the *uplink's*. A mailer only looks in the zone of the node it is calling, so the session to the uplink completed cleanly having transferred nothing and the message sat on disk indefinitely.

  Nothing surfaced it. The packet's flow file was named for the uplink but filed under the recipient's zone, so the pending-mail scan -- which reads a node's address from the directory's zone plus the flow file's name -- reported a node that does not exist (`2:154/10`, for an uplink of `1:154/10`), which the poller then skipped at `debug` level. Every visible signal said success.

  Packets are now filed for the node that will actually be dialled. Three related changes mean this shape of failure is noisy rather than silent if it ever recurs:

  * A flow file entry whose file is missing is **logged** rather than skipped in silence.
  * A node whose live flow entries all point at missing files is **no longer reported as having pending mail**. That state used to put the poller in a dial-every-cycle-and-transfer-nothing loop.
  * A reference is also looked for by name **in the flow file's own directory**. Flow files store absolute paths, so mail that has been moved -- including anything misfiled by this bug before upgrading -- now ships by moving the files, with no hand-editing of flow files. See [UPGRADE](UPGRADE.md).

  Each routed NetMail also logs where it was routed, so the effective route can be confirmed rather than inferred.

* **TIC-announced files can now be forwarded to downlinks** ([#743](https://github.com/NuSkooler/enigma-bbs/issues/743)) — ENiGMA½ could only ever be a **leaf node** for FTN file echoes. A file received from an uplink was imported into the file base and then deleted from the inbound; it was never passed on. There was no way to declare downlinks, no TIC was ever generated, and the `Path` / `Seenby` fields were read but never written. Anyone downstream had to be fed by some other file processor, which in practice meant ENiGMA½ could not be used as a file-echo hub at all — a notable gap for a package that otherwise does full EchoMail and NetMail hubbing.

  Declare downlinks on the TIC area and it forwards, generating a TIC for each:

  ```hjson
  ticAreas: {
      fsx_gen: {
          areaTag:   fsxGeneral
          network:   fsxnet
          uplinks:   [ "21:1/100" ]                // who may publish into it
          downlinks: [ "21:1/200", "21:2/150" ]    // who receives it
      }
  }
  ```

  **Off unless you configure it.** An area with no `downlinks` behaves exactly as before. See [TIC Support](website/src/content/docs/filebase/tic-support.md#forwarding-to-downlinks).

  * **`uplinks` is an access control, not a formality.** Authentication is not per-area: every node in `nodes` is equally able to send you a TIC for any area you carry. Without `uplinks`, a node configured for some entirely unrelated reason could announce a file into an echo it has no rights to and have you relay it to that echo's subscribers under your own address, `Path` and `Seenby`. An area with `downlinks` and no `uplinks` forwards nothing and says so at startup. HTick performs the same check before forwarding.

  * **The loop guard is the part that matters.** A downlink already listed in the TIC's `Seenby` is skipped, as are the sender, the TIC's `To`, the file's `Origin`, and your own addresses on any network. Addresses are compared allowing for the 2D–5D differences that are ordinary in FTN control data — FSC-0087 lets each hop rewrite them — because a strict comparison would fail to notice a system had already seen a file and send it round again.

  * **Forwarding is gated harder than importing.** Importing affects your own file base; forwarding makes other systems receive traffic your `Path` and `Seenby` vouch for. A TIC from the unsecure inbound is never forwarded even if you import from there, and neither is one from a node with no `tic.password` — such a node is never actually authenticated, because the check is simply skipped when no password is configured. A TIC addressed to somebody else is imported but not re-announced.

  * **`Replaces` dequeues.** When a replacement supersedes a file still queued for a downlink that has not collected it, the old file and its TIC are removed from that downlink's outbound. Otherwise a downlink polling weekly would receive both — and the older one has by then been deleted locally, so it would receive neither.

  Problems that would otherwise be silent are reported at startup: an area with downlinks but no resolvable network, a downlink missing from `nodes`, or one with no TIC password.

  * **A system carrying file echoes and no message areas can now import at all.** The import pass was gated on having `messageNetworks.ftn.areas` configured, which TIC processing has nothing to do with — so a file-echo-only system logged "EchoMail export disabled" and then silently did nothing with every file its uplink sent. That configuration was barely reachable before this feature existed; it is the obvious one to try now.

* **Hatching — you can put your own file into an echo you carry** ([#751](https://github.com/NuSkooler/enigma-bbs/issues/751)) — forwarding passes on a file an uplink sent you; hatching originates one. A hub that cannot hatch cannot ship its own nodelist or infopack — it can only repeat what it is told.

  ```
  oputil.js fb hatch <areaTag> <file> [--desc ...] [--replaces ...]
  ```

  The area tag is the FTN one, a `ticAreas` key, because that is what an operator configuring a hatch is looking at and one local area may carry several echoes. Deliberately thin: the per-downlink TIC generation, the loop guard, the unique 8.3 naming, the payload-then-TIC append and the `Replaces` dequeue are all reached through the same code a forward uses, now shared rather than duplicated. A `ticAreas` entry may carry an `areaDesc`, written as FTS-5006 `Areadesc` into TICs you hatch; a forwarded TIC carries whatever the hatching system wrote, untouched.

  See [oputil](https://enigma-bbs.github.io/admin/oputil/) and [TIC Support](https://enigma-bbs.github.io/filebase/tic-support/).

* **Passthrough file areas — carry an echo without storing it** ([#753](https://github.com/NuSkooler/enigma-bbs/issues/753)) — a hub may carry an echo purely for its downlinks, with no interest in keeping the files. `store()` required a local file base area and hard-failed without one, so a hub had to keep an area per echo for files its own users would never browse.

  Set `passthrough: true` on the `ticAreas` entry and the file is held in a transit directory only as long as a downlink still references it, then swept. It is **required explicitly and never inferred** from a missing `areaTag`: a `ticAreas` key is matched against `fileBase.areas` too, so an entry without one may well be a working stored area that inference would quietly turn into a deleting one.

* **An echo carried on more than one network addresses each downlink correctly** ([#757](https://github.com/NuSkooler/enigma-bbs/issues/757)) — TIC forwarding took the network from the *first* downlink's zone and then signed every downlink with it. A hub with several AKAs, or an area carried on two networks, therefore presented the wrong identity to some of its links.

  Each downlink is now addressed from our closest AKA by zone and net, with `nodes.<addr>.tic.network` and then the area's `network` as overrides. `Seenby` lists every AKA in play rather than only one, because a peer matches it against the address *it* knows us by — a `Seenby` naming one address lets a system that knows us by another forward the file straight back.

  The outbound *directory* deliberately stays the area's and is not tied to that choice: the per-node `.bsy` lock is derived from the address by zone, and a flow file written where the lock resolver does not expect it means the tosser and a live BinkP session take *different* locks — which is the whole exclusion [FTS-5005](http://ftsc.org/docs/fts-5005.003) exists to provide. Nothing is lost, since an outbound session presents every one of our addresses in the handshake anyway.

* **A forwarded file and the TIC announcing it are now pruned together** ([#862](https://github.com/NuSkooler/enigma-bbs/issues/862)) — the two are queued in one append, adjacent and in that order, so removing one must remove the other. The tosser's `scrubFlowFileRefs()` knew that; the BinkP side's prune path did not. Pruning a missing payload therefore left its TIC queued, and downlinks were handed TICs announcing files they would never receive. The companion rule now lives in one shared place used by both.

* **Outbound could be dropped on the floor while a mail session was running** — ENiGMA½ appended reference records to BSO flow files without taking the flow file's `.bsy` lock, while the BinkP side rewrites those same files as entries are sent: it reads the whole file, marks a line done, and writes it back. An append landing between that read and that write was **silently discarded**. No error, no log — the queued file simply never shipped, and with nothing left referencing it, its packet sat in the outbound indefinitely. The busier the system, the more often it happened.

  [FTS-5005.003](http://ftsc.org/docs/fts-5005.003) §5.1 puts the requirement on *software*, not on mailers: "A bsy is a main control file that must be used by any software dealing with flow files in BSO […] If a bsy file exists all changes are prohibited in any corresponding flow files." The tosser queueing outbound is exactly that. Both BinkP session paths already took the lock, so the writer was the only unprotected party.

  Because `NNNNnnnn.bsy` is the standard name, honouring it also interlocks correctly with **external mailers** — Binkd takes the very same lock, so neither side needs to know about the other. (The pre-existing `enigma.bsy` flag could never serve this purpose: it is a non-FTS-5005 name in the outbound *root*, so no external mailer has reason to interpret it.) The protocol now lives in one place and is shared by the writer and the mailer rather than reimplemented on each side.

  When the lock cannot be taken the outbound is **not** queued that pass and says so — not writing is what the spec requires, and the next export cycle picks it up. `scannerTossers.ftn_bso.flowLockTimeoutMs` (default 5 seconds) bounds the wait; see [BinkP](website/src/content/docs/messageareas/binkp.md#flowlocktimeoutms).

  **A second, related race** was found by running two instances against each other: when one session ships more than one file to the same node, each file's completion rewrote the whole flow file independently, so all but one entry silently lost its "sent" mark. For mail the entry is deleted after sending, so the leftover reference merely dangles; for a forwarded file echo — where the file stays in your file base and must not be deleted — it looked unsent and went out again on **every** subsequent session. Those rewrites are now serialised.


* **A wildcard could shadow a more specific entry in `nodes{}` and NetMail `routes{}`** -- where several patterns matched an address, which one applied depended on nothing but the order they were written in `config.hjson`. A `"*"` route above `"21:*"` took every message; a `"21:*"` node block above `"21:1/100"` meant that node's `packetPassword` was never the one checked. The **most specific match now wins** regardless of order, which is what the native BinkP mailer already did for its own `binkp.nodes{}`.

  `routes{}` is still consulted before `nodes{}`, so a catch-all `"*"` route claims all NetMail -- AreaFix to your uplinks on other networks included. With ordering no longer deciding the outcome, a more specific route can now reliably send those direct. See [NetMail](website/src/content/docs/messageareas/netmail.md#which-route-applies).

* **The `download` file area ACS was enforced over the REST API and nowhere else** -- a security control that silently did not work. A file area can reasonably let everyone browse while restricting who may actually pull bytes down:

  ```hjson
  someArea: {
      acs: {
          read: GM[users]
          download: GM[donors]
      }
  }
  ```

  `read` was honoured everywhere, so browsing looked correctly gated and the configuration appeared to work. `download` was checked only by `core/rest/routes/files.js` -- over telnet and SSH, where essentially every user is, anyone who could see a file could queue and download it. It was the only ACS scope in the system with no terminal-side enforcement.

  The check is now applied at every path that can move a file to a user:

  * **Queueing** -- `DownloadQueue.add()` refuses an entry the user has no `download` right to, and the file area list shows a distinct indicator (`noDownloadAccessIndicator`, `n/a` in the shipped theme) rather than letting the queue key look broken.
  * **Protocol downloads** -- the send queue is filtered at transfer time. A download queue persists in a user property across sessions, so an item queued while permitted can outlive the permission; being removed from a group now takes effect immediately.
  * **Web download links** -- both single and batch link generation are gated in `FileAreaWeb`, which also covers the browse screen's "generate web link" action. That path never went through the download queue at all.

  Temporary session downloads -- QWK packets, FSE attachments -- are generated for the user on request, carry no ACS of their own, and are unaffected.

* **Message areas can now be created automatically for EchoMail you are not configured for** ([#241](https://github.com/NuSkooler/enigma-bbs/issues/241)) — mail arriving for an unknown FTN area tag was skipped with a warning, and since the packet was then removed, skipped meant *lost*. ENiGMA½ can now create those areas instead. **Off unless you configure it**; a system with no `autoAreas` block behaves exactly as before, and with no network enabled nothing extra runs at all.

  Setup is one command — `./oputil.js mb auto-areas init` — and then a per-network `autoAreas` block. See [FTN](website/src/content/docs/messageareas/ftn.md#automatic-area-creation).

  * **Created areas are read-only, and that means both halves.** They carry no `uplinks`, so nothing is exported. On its own that is not read-only: a local user could still post into an area that looks live and goes nowhere. So they also carry a write-deny ACS. To adopt one, define it in `config.hjson` with your own `uplinks` and `acs` — `config.hjson` always wins over the generated file.

  * **Nothing is ever written to your `config.hjson`.** Created areas go to a generated `auto-areas.hjson` pulled in through `includes`, which merges such that your own file wins. That file can therefore be rewritten on every pass without ever touching a description you wrote by hand.

  * **Real names and descriptions come from the network info pack.** The pack arrives by TIC like any other file; ENiGMA½ looks for it in the file area you name rather than waiting to be told, so one that landed before you enabled the feature counts too. It only renames areas you already carry — a pack lists what the *network* carries, which would otherwise leave you with hundreds of permanently empty areas.

  * **Collisions are refused, not merged.** An FTN tag lower cases straight onto a local area tag, and `PRIVATE_MAIL` would land an echo in everyone's mailbox. A tag already used in any conference, or carried by another network, is refused too, and the reason is logged.

  * **`ignore` and `maxAutoCreate`.** Adding a tag to `ignore` removes it if it was already created, so it is a real un-create. `maxAutoCreate` caps the total ever created for a network rather than the number per run — a per-run cap compounds.

  * **AreaFix rescan is optional, off, and has no default command.** [FSC-0057](http://ftsc.org/docs/fsc-0057.003) specifies `=TAG R=n` and Mystic and CrashMail II implement it, but husky and SBBSecho do not: they read it as a request to *add* an area with a garbage tag, and a husky hub with `forwardRequests` may pass that upstream. There is no portable form, so you state the one your uplink speaks or nothing is sent. Replies are matched to requests actually sent and summarised to you in NetMail.

* **`oputil mb import-areas` imported comment lines as message areas** ([#733](https://github.com/NuSkooler/enigma-bbs/issues/733)) — a leading `;` or `%` line became an area whose tag was the comment character. Measured against real network info packs, importing fsxNet's file echo list produced 18 of them and AgoraNet's 14, written straight into `config.hjson` for you to find and remove by hand.

  The area list parser is now shared between `oputil` and automatic area creation, and it works out the format from the file's **content** rather than its extension:

  * `;`, `%` and `#` comment lines are skipped. fsxNet used `%` in its 2018 pack and `;` in the current one, so both are needed.
  * A FILEBONE *file* echo list — which six of eight surveyed networks ship named `*.na`, alongside their message list — is recognised and sent to `fb import-areas` instead of being imported as areas all tagged `Area`.
  * A list with the columns reversed, description first, is recognised and refused. SpookNet ships one, and the old parser took 35 entries from it with tags like `Aliens,` — nothing on those lines is malformed enough to reject one at a time, so the decision has to be made about the file as a whole.
  * Lines that survive but cannot be used are listed for you before the confirmation prompt instead of being silently dropped.

  `AREAS.BBS` is unchanged: it cannot be told from a plain area list by shape, so it is still only assumed from the `.bbs` extension or `--type bbs`.

* **`oputil fb import-areas` shares that parser**, so a FILEBONE list is recognised by its content rather than its name, and a *file* echo list shipped as a plain `TAG  Description` list — ArakNet's, among others — imports rather than reporting "Nothing to import". FileGate `.ZXX` and FILEBONE `.NA` files produce byte-identical results to before; a multi-digit area level and flags other than `!` and `*&` are now accepted as well. Since a plain list is indistinguishable from a *message* echo list, `import-areas` says so before the confirmation prompt.

* **A missing `includes:` file said the wrong thing on startup** — a file listed in `includes` that does not exist stops the board from starting, correctly, but the message advised running `./oputil.js config new` as though `config.hjson` itself were missing, and printed the placeholder `'{configFile}'` instead of a path. Both now name the file that is actually missing and say what to do about it.

* **A second instance bound nothing, said nothing, and kept running** ([#547](https://github.com/NuSkooler/enigma-bbs/issues/547)) — starting ENiGMA½ while another instance already held its ports produced no error, no `System started!`, and no exit. The process simply sat there, serving no one.

  Node's `server.listen(port, host, cb)` registers `cb` as a one-shot `'listening'` listener: it never receives an error argument, and on a failed bind it never fires at all. Every server treated it as an error-first callback, so `EADDRINUSE` left the startup series in `listening_server.js` waiting for a callback that would never come. Telnet caught the event but logged it at `info` — and the default logging config writes to a rotating file with no console stream, so nothing reached the terminal. The remaining servers had no server-level `'error'` handler at all, so the event fell through to the process-level `uncaughtException` net, which by design keeps the process alive.

  Every login, content, and chat server now binds through a shared helper that listens for both `'listening'` and `'error'` and calls back exactly once, with an error an operator can act on — `EADDRINUSE`, `EACCES` on a privileged port, and `EADDRNOTAVAIL` each get an explanation rather than a bare code. A bind failure is now fatal for **every** server, including NNTP; see [UPGRADE.md](UPGRADE.md).

  * **Startup output now reads in the order things happen** -- the banner, then any configuration warnings, then the server list, then `System started!`. The banner was previously printed at the very end, underneath everything it was supposed to introduce.

  * **Startup now reports what actually bound.** One line per server with its address and port, so a misconfigured or missing service is visible at a glance instead of only in the log. Colour is used only when stdout is a TTY and [`NO_COLOR`](https://no-color.org/) is unset, so piped output and journals stay clean.

  * **Startup failures always exit non-zero.** An error that had already been displayed previously fell through the final handler and the process wound down with status `0`, so service managers and install scripts saw a clean exit from a failed start.

* **BinkP sessions ended on a timeout instead of a clean close** — binkp/1.1 runs a session as a series of batches: another follows any batch that carried more than the two `M_EOB`s, and only an empty batch ends the session. ENiGMA½ stopped after the first one, leaving a conforming peer waiting for an `M_EOB` that never came.

  No mail was lost — it had already transferred by then — but the peer sat until its own timeout (five minutes, for binkd) and then recorded an otherwise successful session as `failed`. With binkd's shipped `try`/`hold` settings, enough of those in a row will put us on hold and stop it calling for a while.

  The cost was ours too: an inbound session parked like that still holds the node's lock, so crashmail queued for that node inside the window is skipped and waits for the next scheduled poll — quietly defeating the point of crashmail. Sessions against binkd now finish in milliseconds and log `done (..., OK, ...)`.

  Peers below binkp/1.1, and any that never identify their version, are treated exactly as before.

* **BinkP GZ compression used the wrong container** ([#723](https://github.com/NuSkooler/enigma-bbs/issues/723)) — [FTS-1029](http://ftsc.org/docs/fts-1029.001) specifies zlib's `compress()`/`compress2()`, which produce the RFC 1950 container: two header bytes and an Adler-32 tail. ENiGMA½ emitted RFC 1952 (gzip) instead — the same deflate payload behind a different header — so every conforming peer rejected it on sight. binkd logs `Decompress <file> error -3` and abandons the transfer; the *sending* side saw nothing wrong and re-offered the same file on every poll, for days. Confirmed here against binkd 1.1a-115 and reported against Mystic 1.12A48.

  Only nodes **without** `archiveType` were affected: ArcMail bundles and archives are already compressed, so GZ is skipped for them entirely. That is the same set of systems as the packet-naming bug in #722.

  * **Both containers are accepted on receive.** The GZ option carries no version, so a pre-fix and a post-fix ENiGMA½ cannot tell each other apart. Inbound data is now sniffed and either container decoded, which keeps a half-upgraded link working in that direction. Only what we *send* changed.
  * **A failed decompression recovers instead of stalling.** FTS-1029 lets a receiver switch compression off mid-session by answering with an `M_GET` carrying an `NZ` token; ENiGMA½ now does that and takes the file again in the clear. If that fails too it sends `M_SKIP`, so the batch finishes rather than hanging to a timeout. Previously the error was logged at `warn` and the session simply stopped.
  * **Compression can be turned off per node** with `gz: false`, for a peer whose decompressor cannot be fixed.

* **BinkP outbound stalled against any peer that asked for NR mode** ([#724](https://github.com/NuSkooler/enigma-bbs/issues/724)) — a peer sending `OPT NR` obliges us to offer each file with an offset of `-1` and wait for it to name the offset it wants ([FTS-1028](http://ftsc.org/docs/fts-1028.001)). We did that, then began sending file data straight away. [FTS-1026](http://ftsc.org/docs/fts-1026.001) requires the answer to `M_GET` to "proceed with transmission of the file requested starting with an appropriate `M_FILE`", and a conforming receiver has already closed the file by the time it sends `M_GET` — binkd discards every data frame that arrives with nothing open, silently. Both sides then waited: ours for the acknowledgement, theirs for the re-announcement, until the five minute session timeout. No mail moved and nothing was logged above `debug`. Note that this had nothing to do with the peer's version: binkd asks for NR whenever a sysop sets `-nr` **or** `-nd` on a node, and `-nd` is common. Fixed, along with four related defects in the same code:

  * **`M_SKIP` wedged the batch** — a skipped file stayed in the in-flight slot forever, producing the same silent stall. binkd sends `M_SKIP` in place of `M_GET` whenever an inbound skip mask matches, so this was a second route to an identical symptom. Skips are now honoured as FTS-1026 intends: non-destructive, the file kept for a later session, the batch carrying on.

  * **`M_GET` for an already-sent file was ignored** — FTS-1026 requires recognising a request naming "a file that have been transmitted, but we are still waiting an M_GOT acknowledge for it" — the race it explicitly warns implementations about. We logged it and moved on, leaving the remote waiting.

  * **Inbound NR started each file twice** — after answering an offset request we left the receive open, so the sender's required re-announcement began a *second* receive of the same file. A FREQ arriving that way pinned the end-of-batch hold above zero and the session never sent `M_EOB`.

  * **`OPT NR` is no longer sent by default** — the frame asks the *remote* to hand us files an offset at a time, costing a round trip each; FTS-1028 says it "should be used only if absolutely necessary". It is now opt-in per node via `requestNR`. Honouring a peer's request remains unconditional, as the spec requires.

  Also removed: a denylist of binkd 0.9.x version strings that switched NR off. It was transcribed from binkd's source, where the identical list drives the *opposite* workaround.

* **BSO outbound correctness & spec compliance** — a set of fixes to the FidoNet-style outbound spool shared by `ftn_bso` and the native BinkP mailer, each checked against [FTS-5005.003](http://ftsc.org/docs/fts-5005.003) (*Advanced BinkleyTerm Style Outbound flow and control files*). All four caused mail to sit in the spool undelivered with nothing logged at any level, including `trace`. See [UPGRADE.md](UPGRADE.md) for recovery of anything already stranded.

  * **EchoMail export to a node without `archiveType`** ([#722](https://github.com/NuSkooler/enigma-bbs/issues/722)) — a node with no `archiveType` exports bare packets rather than ArcMail bundles. Those were renamed onto a BSO netmail flow file name with no separating dot (e.g. `43792ae5cut` instead of `43792ae5.cut`), which nothing — this mailer or any other — could ever match. The basename was also a message serial number rather than the destination's net/node, so simply restoring the dot would have decoded it as a phantom address. Un-archived packets now ship as flow file references (`NNNNnnnn.?lo`), exactly as ArcMail bundles and NetMail already did. This is also what the spec requires: §3.1 gives a netmail flow file a one-to-one correspondence with its destination, so a node can hold exactly one at a time, while a single export routinely produces several packets.

  * **Direct-attach packets are renamed on the wire** — §3.1 requires that a netmail flow file (`NNNNnnnn.?ut`) "must be dynamically renamed at the moment of sending to a remote system with a unique name and extension `pkt`". ENiGMA½ sent it under its `.?ut` name, so although the transfer succeeded, the receiving system's tosser did not recognize what arrived as a packet. Such files — which other software, or a sysop, may legitimately place in the outbound — are now sent as a unique `NNNNNNNN.pkt`.

  * **Upper case outbound files are now found** — §2 asks that software "be able to handle both" upper and lower case BSO filenames. The mailer's pending-mail scan was case-insensitive but its per-node lookup was not, so a node with upper case flow files (from `fileCase: 'upper'`, or an outbound inherited from a DOS-era mailer) was reported as having mail, dialed every poll cycle, and then sent nothing. Lookups, `.bsy` locks, and `.pnt` subdirectories are now all matched case-insensitively.

  * **Point addresses are now polled and shipped** — §2 puts a point's flow and control files in a `NNNNnnnn.pnt` subdirectory of the boss node's outbound. `ftn_bso` has always written that layout, but the native BinkP mailer had no knowledge of it: point mail was never sent, and polling a point address served it the boss node's mail instead. Points are now scanned, shipped, and locked in their own subdirectory.

* **Multi-network BSO outbound fix** — `ftn_bso` (the scanner/tosser) and the native BinkP mailer used two independent rules to decide which FTN network owns the bare `outbound/` spool directory. With two or more networks configured and no explicit `scannerTossers.ftn_bso.defaultNetwork`, the two disagreed: outbound NetMail and EchoMail for the first-listed network was written to `mail/ftn_out/<network>/` but looked for in `mail/ftn_out/outbound/`, so it was never sent — and never logged an error. Both sides now share a single resolver (`defaultNetwork` when set, otherwise the first listed network), network names are matched case-insensitively, and mail already queued under the previous layout is picked up and sent automatically. See [UPGRADE.md](UPGRADE.md) for details.

* **A file could not be found by its own name** — `FileEntry.findFiles()` and the message base ran query *values* through a `sanitizeString()` that escapes MySQL style: doubling `"` and backslash-escaping `\`, `%` and the control characters. SQLite's only string-literal escape is a doubled quote, so all of that arrived as **extra characters** and a value could not match itself. A file named `100% Pure.zip` or `back\slash.zip` was simply not findable.

  Never an injection — the one escape that mattered was correct — but wrong, so values are now bound parameters rather than interpolated into the statement. The one interpolation that remains, a sort column, is checked against an allow-list, since a column name cannot be a bound parameter.

  A wildcard `Replaces` was the same bug with teeth ([#864](https://github.com/NuSkooler/enigma-bbs/issues/864)): a TIC's `Replaces` is a DOS glob matched against the stored short file name, and the conversion turned `*` into `%` before handing the result to the escaper — so every wildcard came back out as the literal two characters `\%`, and with no `ESCAPE` clause SQLite read that backslash literally. `Replaces NODELIST.*` therefore matched nothing, `tic.allowReplace` stored a **second copy** instead of superseding, and the old file stayed live in the base and queued for every downlink that had not collected it. An exact `Replaces NODELIST.246` worked, and so did `NODELIST.2?6`, which is what made it so quiet.

  * `oputil.js user import-ssh-key USERNAME KEYFILE` — imports a SSH public key for a user from a file, validates the key, and stores it for SSH key-based login
  * `oputil.js user remove-ssh-key USERNAME` — removes a user's stored SSH public key
  * `oputil.js user info USERNAME` now displays SSH key info (algorithm, SHA256 fingerprint, comment) when a key is on file

* **File Base: Wildcard/Recursive Storage Tags** ([#194](https://github.com/NuSkooler/enigma-bbs/issues/194))

  Appending `/*` to a storage tag path enables recursive scanning of all subdirectories:

  ```hjson
  storageTags: {
      scene_files: "/path/to/scene/*"   // walks all subdirs
  }
  ```

  * Files found in subdirectories are indexed with their `relPath` (e.g. `2024/April`) stored in the database, so same-named files in different subdirectories are tracked as distinct entries.
  * When an area mixes flat and wildcard tags, flat tags are scanned first and their directories are excluded from wildcard scans to prevent double-indexing.
  * `.enigmaignore` files (gitignore syntax) can be placed anywhere in a wildcard tree to exclude files or directories from scanning.
  * Startup warns on malformed wildcard patterns (e.g. a bare `*` not at the trailing `/*` position).
  * New database column `storage_tag_rel_path`; automatically added to existing installations on first startup.

* **Bug Fixes & Stability**

  * Fixed ENiGMA segfault on ARM64 Linux (Raspberry Pi) — see [#620](https://github.com/NuSkooler/enigma-bbs/issues/620)
  * Improved `install.sh`: better distutils availability check ([#631](https://github.com/NuSkooler/enigma-bbs/issues/631)), additional script improvements
